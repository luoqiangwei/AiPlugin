# CodeReview

审查指定变更或代码范围，沿调用链找出可触发的错误，排除已有保护，再给出有证据的结论、修复方向和验证结果。

## 按运行场景、语言和框架选择审查资料

[references/index.json](references/index.json) 只维护分类、适用条件和文件路径。先确认本次变更在哪里运行、由什么语言实现、使用哪些框架，再读取相关内容；三种维度相互补充，不是互斥的项目分类。

索引中的 `contexts` 处理 Android 应用、AOSP、内核和浏览器/HTTP 的运行约束；`languages` 处理语言与标准库语义；`frameworks` 处理框架或运行库的实际行为。资料只补充各自特有机制，通用判断统一使用下面的流程。

运行场景下的 `checks` 是按改动机制选择的专项检查。例如 Android 的兼容性、SELinux、并发、ANR 和 system_server Watchdog 各有独立细则；只加载被本次变更触发的专题。普通 App 不承担平台全量 CTS 门禁，App ANR 与 system_server Watchdog 也不能按同一种超时处理。

BPF 按内核执行专题审查，Android 平台集成再补 AOSP 下的 BPF 专题；实现语言仍按实际源码选择。高频路径先检查 helper 滥用、重复查表、循环放大、过度拉包/复制和事件输出，再检查并发与策略语义。只有改到构建、加载、权限或生命周期时才展开对应链路；verifier 通过不代表成本或业务正确。

例如，AOSP 的 Rust 服务读取 AOSP 场景和 Rust 语言，涉及驱动才补内核；Rust 内核代码不套用 Tokio；Java 编写的 Spring HTTP 服务读取 HTTP 相关场景、Java 和 Spring；浏览器 TypeScript 读取浏览器相关场景、JavaScript 和 TypeScript，不扩展到未涉及的服务端链路。

只按本次变更选择资料，不因仓库含某依赖或扩展名就全量加载。不要求三个维度都有对应文件：普通 Rust CLI 可以只用通用方法与 Rust；没有专项模块的框架按真实契约补查，不声称已有完整覆盖。

- 复杂状态、设计、重构、并发和测试：[通用代码审查要点](references/common/quality.md)，包含反例、修复和验证方法。
- 外部输入、权限、敏感数据、依赖和漏洞修复：[安全推导与处置](references/common/security.md)。
- 新增或修改日志、失败处理、关键状态变化、降级与恢复路径：[日志级别与诊断完整性](references/common/logging.md)。既检查多余日志，也从执行分支反查应记录却未记录的事件。
- `references/sources/` 仅保存溯源和版本信息，不是执行前必读内容。只有版本敏感、规则存在争议或需要精确出处时才查对应条目。

## 通用 Review 方法

### 1. 固定范围与基线

- 读取仓库约定、变更说明、相关设计与测试。明确本次是差异审查、指定文件审查还是全量专项审计；用户已有范围时直接遵守。
- 记录仓库/模块、base/head 或工作区状态。对 PR 使用真实目标分支与正确的 merge base；区分已提交、暂存、未暂存和未跟踪文件，避免遗漏或重复计入。
- 未指定范围时，先检查本地变更并说明采用的范围；无法确定且会改变结论时再请求必要信息。全量审计说明入口与覆盖范围，不能把抽样描述成全部覆盖。
- 从构建文件、锁文件、配置与部署描述确认版本、运行时、编译选项、target SDK、产品分支、数据库和代理。不要用本机版本代替目标环境。

### 2. 先还原契约，再读实现

从调用者、测试和数据约束中还原四件事：哪些输入合法、成功后保证什么、失败后允许留下什么、谁拥有状态和资源。用一句可判真假的话描述关键不变式，如“失败后余额不变”“每个请求最多扣款一次”“注销后不再执行回调”。不要只写“保证线程安全”等无法验证的目标。

阅读范围内的变更行，追踪调用方、实现、权限检查和清理分支。对重构同时比较旧/新行为；对缺陷修复确定旧行为如何违反契约。可观察行为包含返回值、异常、持久化、外部调用、顺序、资源所有权和公开接口，不只包含页面结果。

对高风险路径画出简短链路：`入口 → 身份/权限 → 校验/解析 → 状态或资源操作 → 输出/持久化 → 清理`。标出信任边界、对象所有权、线程/任务、事务和版本边界。删除代码、配置、迁移与测试也是变更的一部分。

### 3. 用已提炼的规则寻找反例

| 审查主题 | 实际执行的判断动作 |
|---|---|
| 输入校验与状态约束 | 找到每条创建/修改路径；用零值、极值、反序列化、额外字段尝试绕过校验；确认验证后未被可变别名改写。 |
| 失败原子性 | 按副作用顺序，在每一步假设失败；列出已发生的写入和外部动作，检查是否仍满足失败契约。 |
| 对象所有权与可变数据 | 对每个传入/传出的可变引用问“谁还能修改它”；区分只读视图、浅拷贝、独立快照和所有权转移。 |
| 类型安全 | 追踪外部数据、类型转换和表示变化，区分类型系统已提供的保证与仍需验证的条件；具体语义按对应语言判断。 |
| 接口设计与封装 | 找出调用者必须知道的内部顺序、标志、表示和配对清理；若同一约束散落多处，定位具体失配点。 |
| 重复代码与业务规则 | 假设一条业务规则改变，找必须同步修改的位置；同一变化理由才考虑集中，不因代码相似强行合并。 |
| 并发与同步 | 写出两个执行者的最短交错时序，检查“判断→使用/修改”是否由同一原子边界保护；分别证明发布、互斥和回收。 |
| 异步任务、取消与资源释放 | 推演相关等待点的取消、满队列提交和关闭时回调；核对副作用、积压上限、上下文和释放责任，再选有代表性的点验证。 |
| 错误处理与恢复 | 将异常、超时、无权限和不存在分别带回调用者；检查是否误报成功、失败放行或对已完成动作再次重试。 |
| 日志与可诊断性 | 检查关键失败、状态变化、降级与恢复是否留下必要证据，级别是否匹配结果；再核对责任边界、发布可见性、上下文、敏感信息、频率和构造成本。 |
| 测试有效性 | 假设删掉关键授权/边界检查或重复一次副作用，现有断言是否会失败；验证发生缺陷的真实边界。 |
| 兼容性与演进 | 对照旧调用者、新实现和回滚状态，检查字段布局、默认值、错误语义、迁移和条件构建。 |
| 性能与资源开销 | 算清受输入放大的次数、查询、分配、排队和阻塞位置；与实际预算比较后再判断性能缺陷。 |

按变更选择相关主题，复杂情况使用通用代码审查要点中的推演步骤，再检查运行场景、语言和框架特有机制。发现“长函数”“缺少 DTO”“用了 unsafe”“用了线程池”都只是继续调查的信号；必须说明哪条契约被什么合法或攻击输入破坏。架构偏好、行数和覆盖率不能独立成为缺陷。

### 4. 排除误报，并验证关键结论

- 对每个候选问题找反证：上游是否已校验、所有入口是否受保护、API 是否复制/持有资源、配置是否关闭该路径、分支是否回移修复。无法确定关键条件时标为待确认，不当成确定缺陷。
- 候选问题至少补全 `触发者/输入 → 经过的代码 → 被破坏的不变式 → 可见后果`。每次提出修复，都反问修复是否只移动了风险：换异步锁不消除锁环，增加线程不限制排队，浅拷贝不隔离嵌套对象，外层测试事务不证明生产事务生效。
- 漏洞判定写出 `攻击者能力 + 入口 + 数据流/控制流 + 缺失控制 + 可达影响`。危险函数、版本命中和历史 CVE 仅是线索；依赖也要区分实际交付、功能启用和可达性。
- 优先运行仓库现有的相关检查、针对性测试或最小复现；用边界、负向、并发与失败用例验证实际风险。静态推导足够清楚时不强制制造 PoC；不运行测试时说明原因。
- 编译、lint、扫描器和测试结果分别报告。未运行、环境受阻、失败、通过不能混写；通过一次不代表没有漏洞。不要为了形式重复无关的大规模检查。
- 本地规则足以支持的判断直接执行；当结论取决于具体版本的 API 语义、修复范围或未知契约时，再核对相应官方资料。离线时把缺少的条件单列，不把“还没访问链接”作为停止已能完成的审查的理由。

### 5. 形成可操作结果

默认交付审查报告。只有用户要求修复时才改代码；发布评论、提交审查结论、创建工单等外部动作遵守用户授权。修复后重新验证并审查受影响的调用链。

按影响与紧迫性排序，置信度单独标记；本表是 Review 优先级约定，不是 CVSS 分数映射：

| 优先级 | 判定依据 |
|---|---|
| P0 | 已有充分证据表明需要立即处置的广泛严重后果，如正在暴露的核心权限失守或不可恢复数据破坏；极少使用。 |
| P1 | 在项目实际使用或部署条件下可触发的严重安全、数据、崩溃或关键功能问题，应优先修复。 |
| P2 | 有明确触发条件和实质影响的常规缺陷，需要修复。 |
| P3 | 影响较小但具体、可操作的问题；纯偏好另列为可选建议。 |

每个 finding 包含：

```text
[P2] 动作明确的标题
位置：文件:起止行（尽量短，差异审查尽量落在变更行）
证据状态：已复现 / 静态证据充分 / 待确认（缺少什么）
触发条件 → 实际行为 → 影响；指出相关调用或配置证据。
修复：最小有效方向，以及必要的兼容/回滚考虑。
验证：能捕获此问题的回归场景；区分已执行结果和建议。
依据：相关审查主题 / CWE / 版本化规范（有直接对应关系时填写）。
```

先列可确认的发现，再列待确认问题、可选建议和验证摘要。同一根因合并，影响不同的入口列在同一条下。差异审查聚焦新增或被此次变更放大的问题；原有问题如需报告，明确单列。

结尾说明审查范围、实际运行条件、已执行检查与结果、未覆盖或受阻部分。无明确发现时直接说“本次范围内未发现可确认的问题”，并给出覆盖与验证限制；不要声称“绝对安全”或用建议凑数。

## 维护知识库

新增知识必须落实为“什么时候进入检查 → 如何推导失败 → 什么证据足以确认 → 哪种情况不成立 → 如何修复与验证”，不能只增加链接、书名或原则口号。示例用于说明机制，不能直接作为生产补丁。

新内容先判断属于通用方法、运行场景、语言还是框架，放入对应目录并更新索引；不同维度不再混列，也不为每一种组合复制文件。主体按代码变化与可确认的缺陷组织，把不会改变判定的原理、版本路径和 API 导读移出执行规则。用自然标题表达主题，不引入人工编号。依据保存在 `references/sources/`，区分已读正文、公开摘录与仅有目录的信息。

规范版本、SDK 行为、公告影响范围和支持周期会变化；只对影响当前结论的动态条目复核。本地保存原创归纳、判定步骤和必要示例，不复制书籍或手册全文。
