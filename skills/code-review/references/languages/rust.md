# Rust

Rust 语言与标准库规则适用于不同运行场景。先记录实际 rustc、edition、target、features/cfg/no_std、panic 策略和依赖；MSRV、Cargo 锁文件按项目是否采用核对，AOSP/内核可使用自己的构建系统。平台权限、内核执行上下文、HTTP 边界和 Tokio 行为分别读取对应场景或框架资料。

## 选择检查路径

| 代码变化 | 进入的检查 |
|---|---|
| unsafe、原始指针、set_len、MaybeUninit、手工 Send/Sync | safe 与 unsafe 边界 / Send 与 Sync：从 safe 调用者反推每条 Safety 前提 |
| FFI、回调、析构、用户回调或 panic | FFI 所有权 / panic 与析构：用所有权与中途退出检查边界 |
| async、Future、Drop | 检查暂停与销毁的状态；使用 Tokio 的任务、锁或超时 API 时，再读取 Tokio 框架规则 |
| 输入解析、Result、feature、依赖、平台分支 | 输入与数值转换 / 错误传播 / 依赖与工具链 / 特性与兼容 / 平台命令与路径：验证真实构建及失败语义 |

编译器检查通过不代表业务安全或 unsafe 抽象健全；出现 unsafe、unwrap 或同步锁本身也不是 finding。

## safe 抽象与 unsafe 契约

**需要保持的事实**：所有合法 safe 调用都满足内部 unsafe 操作的前置条件；这一保证覆盖正常、错误、panic、并发和析构路径，而不是只覆盖当前一个调用者。

执行顺序：

1. 对每个 unsafe 操作写一行前提：有效地址/对齐、已初始化范围、单一分配、存活期、别名/可变性、类型有效值，以及分配器与释放约定。使用具体 API 的 Safety 契约，不能只写“指针有效”。
2. 从所有 safe 入口反向追踪：前提由类型、运行时检查、拥有关系还是外部承诺保证？safe API 不能把任意调用者必须遵守的内存安全条件仅藏在普通注释里。
3. 查看前提成立后是否会被破坏，例如验证后原始指针仍被 C 侧修改、Vec 重新分配、用户回调 panic 或其他线程改变共享状态。
4. 对 `unsafe impl Send/Sync`，分别证明转移和共享，不把 Arc 当线程安全证明；检查泛型参数、线程绑定 handle 与跨线程 Drop。

```rust
// 风险：任意 safe 调用者可提供非法 UTF-8；普通注释不能约束输入。
pub fn label(bytes: Vec<u8>) -> String {
    unsafe { String::from_utf8_unchecked(bytes) }
}

// 一种修复：在抽象内部验证，错误作为接口契约返回。
pub fn label(bytes: Vec<u8>) -> Result<String, std::string::FromUtf8Error> {
    String::from_utf8(bytes)
}
```

若业务接受替换非法序列，可明确采用有损转换；不要在未确认业务语义时悄悄改变字节含义。若库确实提供 unsafe API，调用者契约仍须准确，不能用改成 unsafe 掩盖本可安全封装的普通接口。

**排除误报**：输入来自仍受类型与所有权保证的 `&str`，或所有合法入口都在当前抽象内部验证且之后无法被修改，可能已满足 UTF-8 前提。私有辅助函数的前提也可以由其全部调用者维护，应读取实际调用关系。

**验证**：用最小 safe 调用构造反例，而不是先写更多 unsafe。覆盖空/ZST、边界、非法 UTF-8、重新分配、panic 和析构；Miri 可验证具体执行的部分 UB，不能证明所有调用组合。`capacity >= n` 只说明分配空间，不说明前 n 个元素已初始化；`set_len` 的证明必须包含实际初始化进度。

## FFI 所有权、panic 与析构

**需要保持的事实**：同一资源只有约定的释放方；借用不超过真实所有者的存活期；回调注销后不再访问已释放对象；任何可退出点都留下可安全 Drop 的状态。

先为 FFI 参数写出五个答案：谁分配、谁释放、谁可以保存指针、可在哪些线程使用、错误/注销何时完成。`repr(C)` 只规定适用类型的布局规则，不会让 `String`、`Vec` 或 trait object 自动变成 C 可理解且可释放的对象。

```text
风险：Rust 把局部 Vec 的指针交给 C 保存 → Rust 返回后 Drop Vec → C 回调读悬空地址
修复：若 C 只同步借用，契约禁止保存；若 C 需长期持有，转成有唯一释放函数的拥有句柄，
      注销要阻止新回调并等待在途回调结束，然后再释放句柄。

风险：ptr::read 移走字段 → 调用户函数生成新值 → 用户函数 panic → 原字段被再次 Drop
修复：在调用可能 panic 的代码前放入有效替代状态，或使用负责恢复/清理的 guard；
      可用安全的 replace/take 方案时优先采用，不让暂时无效的字段跨越可退出点。
```

从 C 指针构造 slice 还要检查：元素数与字节数不能混淆；总字节数的计算不溢出、不超过 `isize::MAX` 且指针范围不绕回；零长度也不能直接把 null 交给要求非空对齐的 Rust slice 构造器；正长度范围需属于同一分配、正确初始化且在借用期间存活。C 可合法传 null/0 时，应先在边界映射为空 slice，而非只检查 `len <= max`。

panic 与 ABI 要分别看：是否允许 unwind、Rust 是 abort 还是 unwind 构建、外部异常是否可能进入 Rust。不能笼统声称“跨 FFI panic 一定可恢复”或“catch_unwind 能捕获所有失败”；捕获后也仍须证明状态有效。

**排除误报**：同步调用期间有真实拥有者保持存活、C 契约明确不保存指针，或者生成绑定/句柄类型已保证释放配对，应作为反证；不要强制每次 FFI 都转交所有权。

**验证**：C/Rust 两侧一起测试合法与非法参数、回调与注销竞争、部分初始化、用户回调 panic、重复关闭。正常测试只能验证一次路径；对精确所有权结论补充控制流与 Drop 证明，native 部分用适合的 sanitizer。

## Future 的暂停与销毁

语言层先检查 Future 被轮询时执行什么、暂停期间持有什么、销毁时哪些字段和资源被释放。销毁 Future 不自动撤销此前已经发生的数据库、文件或网络副作用。取消后业务是否丢数据取决于具体操作契约，不由 async 语法保证。

若变更实际使用 Tokio，再按框架索引读取任务调度、锁、`select!` 与超时的规则；其他运行时按其自身契约判断，不能由 Rust 语言直接推出 Tokio 行为。

## 输入、错误与构建配置

| 审查主题 | 执行判定 | 修复与排除误报 | 有区分力的验证 |
|---|---|---|---|
| 输入与数值转换 | 从外部长度到转换、乘加、分配、递归逐步计算上界；检查 `as` 截断和 debug/release 算术差异 | 使用可失败转换/checked arithmetic 与业务预算；输入已由窄类型限制时先证明范围，不机械加检查 | 超界/截断/深层输入、最低支持位宽；错误必须先于大分配或副作用 |
| 错误传播 | 对每个 unwrap/expect/忽略结果判断失败能否由正常外部条件触发，失败后服务是否仍符合契约 | 对预期失败返回 Result；对不可破坏不变式的断言可保留。保留 JoinHandle 结果和必要上下文，避免日志泄露秘密 | 断连、磁盘/上游失败、任务 panic；验证错误既被观察又不会误报成功 |
| 依赖与工具链 | 分开检查最终依赖、build.rs/proc-macro、工具链/std、native 库与交付产物 | RustSec/锁文件命中后核对功能和真实修复；信息型维护告警不等于可利用漏洞 | 真实 feature/target 依赖树、公告条件、修复后产物；零告警不能覆盖未知问题 |
| 特性与兼容 | 对 API/trait bound、公开错误、cfg 和特性变化列出原本支持的调用组合 | 不要求互斥 feature 同时启用；应用按交付矩阵，库还要看下游合法组合与 MSRV | 最小/默认/关键受支持组合、目标平台、旧调用者编译及序列化兼容 |
| 平台命令与路径 | 输入控制实际执行文件、参数、环境、工作目录或路径哪一部分？目标平台是否有额外解释层？ | 直接受控可执行文件+参数通常优于 shell；Windows batch 等仍按其解析契约判断，不能把 raw_arg 当转义修复 | 目标平台下特殊参数与错误分支；核对实际 std/toolchain，不能只看 Cargo.lock |

依赖历史漏洞的可迁移规则是：查清真正的解释器与生效构建，而非记住版本号。Windows batch 参数转义问题必须追到实际 `.bat/.cmd` 调用；其他平台的普通 Command 参数不能由此自动判为注入。

每条 finding 写出一个合法调用或可达失败时序、违反的契约和影响；明确是内存安全、业务一致性还是可用性。fmt/Clippy 用于减少表面噪声；Miri、fuzz 与并发测试分别检验具体假设，均不能代替契约证明。
