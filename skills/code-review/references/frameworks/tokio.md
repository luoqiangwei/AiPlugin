# Tokio

仅在本次变更实际使用 Tokio 时读取。先确认依赖版本、runtime 类型、worker、任务与资源的所有者；Rust 内核模块、普通同步 CLI 或其他异步运行时不能直接套用 Tokio 的具体 API 规则。语言层的所有权、Future 与析构先按 Rust 语义判断。

## 等待、共享状态与取消

**需要保持的事实**：任务暂停不阻断自身进度所需的线程或锁；取消后的数据、状态与副作用符合该操作约定的交付和恢复语义。允许放弃的预取、遥测或尽力交付结果，不因被丢弃就构成缺陷。

审查时在每个 `.await` 前后写出三列：`当前持有资源 | 已发生副作用 | 取消时由谁恢复/完成`。同时读取被等待操作的取消语义；不能由 async 或超时包装推断自动回滚。

```rust
// 风险：guard 跨越网络等待；另一任务可能需要同锁才能完成该网络操作。
let guard = state.lock().unwrap();
send(guard.request()).await?;

// 修复形状：只在锁内构造拥有的数据；释放后等待。
let request = {
    let guard = state.lock().unwrap();
    guard.request_snapshot()
};
let reply = send(request).await?;
// 如状态可并发变化，按请求版本/业务规则决定是否接纳 reply，而非盲写旧结果。
```

同步 mutex 在短小、没有跨 await、无高竞争的临界区可能完全合适；替换成异步 mutex 只能改变等待方式，不能解决锁顺序或逻辑死锁。隔离阻塞操作时还需约束并发量，避免把无界任务转移到另一个线程池。

对取消更要检查“已取走但未提交”的空档：例如先从队列移除消息，再等待持久化；超时分支 drop future 后，消息可能已不在队列中。可用持久进度、显式确认/重投、事务性提交或协调停机保持不变式，选择与实际投递语义相符的方案。

`select!` 的未胜出分支会停止继续轮询并可能被丢弃；重试一个取消不安全的读/写可能丢弃或重复部分进度。保存进度或复用持续存在的操作状态，不能只在外层多加一次循环。

**排除误报**：若被调用操作在取消前无外部副作用，或事务/持久队列已负责回滚与重投，则无需再造一套恢复机制。独立运行的任务与等待它的句柄需要分开分析，不能把取消等待当作任务取消。

**验证**：选择实际可达的接收、写入和提交边界推演取消/超时/断连，再验证关键场景。断言交付、允许的丢弃及副作用次数符合契约，资源最终回收，而非只断言返回了 timeout；不为不存在的交付承诺增加恢复协议。

## 取消与任务的区别

丢弃 Tokio 的 JoinHandle 会分离已运行的任务，不能据此认为任务停止；检查任务究竟由谁持有、关闭时如何通知和等待。`timeout` 或 `select!` 停止等待不表示远端副作用回滚；对已读出队列的消息、写入一半的数据及已确认的远端请求，按实际操作的取消契约处理。

若任务已在执行阻塞代码，取消信号未必能立刻终止它；为该操作设计实际的超时、中断或完成责任。隔离阻塞任务仍须核对积压、并行数和关机行为。
