# Android 无响应与组件期限

本文件用于主线程阻塞、启动初始化、输入窗口、广播、Service、JobService 或 Provider 调用变化。先读调用链；协程、线程池和 `goAsync()` 都不能单独证明任务在期限内完成。系统服务 Watchdog 的监测对象与应用 ANR 分开判断。

## 先定位谁在等谁、期限从何处开始

记录设备/API、`targetSdk`、OEM/平台分支、构建类型、进程冷暖状态、触发组件、ANR subject、输入/广播标志和事件时间。默认 AOSP/Pixel 时间不能直接套到所有设备；产品自己的超时日志也不自动等于系统 ANR。

| 进入条件 | 截止事件与应查线程 | 预算来源和易漏时间 |
|---|---|---|
| 输入分发超时 | 应用处理输入；先查 main，再查锁持有者/远端 | 输入分发器与窗口配置；主线程先前排队工作也会阻挡输入 |
| 没有焦点窗口 | 可接收相应输入的焦点窗口建立 | 查首帧、窗口可聚焦性和焦点切换；不要求一定存在阻塞栈 |
| 广播超时 | 同步 `onReceive()` 返回，异步 `PendingResult.finish()` | 平台版本、`FLAG_RECEIVER_FOREGROUND`、CPU 调度情况；包含必要的进程冷启动与排队 |
| 执行 Service 超时 | `onCreate/onStartCommand/onBind` 完成；main | 平台服务执行计时与前后台分类；包括冷启动及其他组件占住 main |
| Job 回调无响应 | `onStartJob/onStopJob` 及时返回；main | 系统回调响应期限，不是 Job 的全部运行时长；显式 ANR 还核对平台与 target 条件 |
| 用户发起 Job 通知迟到 | 要求通知的 Job 按时调用 `setNotification` | 对应 API 的通知期限；不能等远端数据到齐后才通知 |
| Provider 无响应 | 远端调用完成；Binder 线程或冷启动 main | 实际调用/框架的检测配置；包括远端进程启动、查询及 Binder 等待 |

审查时标出 `系统开始计时 → 等待进程/消息 → 进入回调 → 投递/排队 → 完成信号`，不要只测函数体。库名含 async 或方法带 `suspend` 不表示内部不会阻塞，`runBlocking/Future.get/join/await` 要继续追到完成者。

## 输入卡住、主线程等锁或等结果

**进入条件**：输入、绘制或生命周期回调新增数据库/文件、同步 Binder、锁、Future、闩锁或昂贵计算；worker 也访问主线程持有的状态。

```text
main: onClick → workerFuture.get() ─────────────┐
worker: load → post(main, deliver) → 等 deliver ┘  main 无法消费队列

main: 等 L → worker 持 L → 同步 Binder 到进程 B
B: 等磁盘/设备/另一个锁                    输入预算仍在消耗
```

沿 `get/monitor/BinderProxy.transact` 找到具体任务、锁持有者和远端回复线程；区分运行中计算、锁等待、可运行但未获 CPU、I/O 与 GPU/系统停顿。单张 main 栈只给采样点，不能证明全部耗时由顶部方法造成。

**确认与反证**：可达用户路径确实同步等待不受控依赖，或有完整等待环，可确认静态阻塞风险；同版本 trace/ANR 记录对应超时后才称已复现 ANR。短且有界的临界区、只由 worker 使用的 Future、与本次事件不重叠的慢任务不能直接推导输入 ANR。

**最小修复**：移除 main 的同步结果等待，让结果异步回到当前状态所有者；锁内只捕获独立快照，锁外执行 I/O/IPC。库负责把实际阻塞操作切到适当 dispatcher；禁止以新开线程后立即 `join()` 作为修复。worker 的完成路径也不能同步等待 main。

**区分性验证**：用可控依赖闩锁让 worker 到达慢调用后暂停，在不释放它时发真实输入并检查 UI/回调继续推进；再释放、断言只提交当前结果。若确认 ANR，保留对应系统记录与 trace；自动化等待应有上界并清理闩锁，不用一次长 `sleep` 充当因果证据。

## 首帧、窗口与进程初始化

**进入条件**：Application、静态初始化、依赖注入、SDK 初始化 Provider、数据库升级、首个 Activity 或窗口 flags 变化。

```text
广播/Service/Provider 请求 → 冷进程 → Provider 初始化 + Application 初始化
                         → 组件回调尚未开始，组件的预算已在流逝
Activity 启动 → 长初始化/首帧迟到 或 窗口不可聚焦 → 按键无可用焦点目标
```

检查合并 Manifest 中自动初始化的 Provider，追到真正执行的初始化器；`ContentProvider.onCreate()` 在 main，不能因数据查询通常在 Binder 线程而漏审。延后打开/升级数据库后，还要检查首次查询的线程、锁和耗时，避免把阻塞转移到首次交互。

**确认与反证**：无焦点 subject 配合窗口状态、首帧/焦点时间线才能归因；一个有意不可聚焦的覆盖窗口未必有错，须确认原本应该接收输入的窗口也不可用。慢启动与 Provider 查询超时分别定位；热启动正常不能反证冷启动问题。

**最小修复**：只保留组件立即需要的轻量初始化，其余按真实依赖延后或异步执行；保证首个可交互窗口在正确时机可聚焦。必要依赖未就绪时表达加载/失败状态，不在 main 同步等初始化，也不绕过必须的初始化契约。

**区分性验证**：分别从 Activity、广播、Service、外进程 Provider 调用冷启动；受控暂停初始化依赖，记录回调进入、首帧与焦点变化。移除错误窗口 flag 后验证按键目标；只检查页面截图或缩短平均启动时间不足以覆盖焦点/尾延迟。

## 广播异步处理仍有完成责任

**进入条件**：`onReceive()` 工作、注册 Handler、`goAsync()`、执行器或异常/取消路径变化。

```text
system_server 分发 → 冷启动/接收线程排队 → onReceive → goAsync → worker 排队
→ 有界工作/持久化交接 → finish                      整段共用广播预算
风险：共享池被长任务占满 → 广播任务未开始 → finally 也没有执行
```

逐条列正常、参数拒绝、执行抛错、提交拒绝、队列取消与关闭路径。取得 PendingResult 后明确唯一完成责任；已开始执行的任务通常用 `finally` 完成，提交前失败须由接收方收尾；未开始即被移除的任务不能依赖其 `finally`。不能先 `finish()`，再把尚未可靠交接的必要工作留给任意线程。

**确认与反证**：缺失可达的 `finish()`、确定的池饱和或无界依赖可确认风险；仅出现 `goAsync()`、worker 或 main idle 不能证明安全，也不能据此断定已 ANR。自定义接收线程只改变接收位置，排队与广播期限仍须核对。

**最小修复**：接收路径完成必要的短处理或可靠调度交接，及时结束；隔离长阻塞任务，限定容量并明确拒绝策略。`goAsync()` 允许回调返回后继续处理，不重置或延长该次广播预算；长工作选择适用的持久调度机制，避免无界线程作为默认修复。

**区分性验证**：用闩锁占满共享 worker 后投递广播，检查广播任务能否开始；分别强制异常、拒绝、队列取消，统计完成一次及交接结果。释放 worker 后确认没有重复副作用；改进后仍测冷进程入口，因为初始化也消耗预算。

## Service 与 Job 回调的不同结束事件

**进入条件**：服务启动/绑定、前台提升、Job 开始/停止、通知构造或任务取消变化。Service 组件并不自动运行在 worker；Job 生命周期回调也在 main。

```text
main: Service.onStartCommand → 网络/Future 等待 → onStartJob 尚不能执行
main: onStopJob → worker.join → worker 等 main 清理回调 → 停止回调也被堵住
修复: main 记录任务状态并投递 → 及时返回；worker 异步报告完成/停止
```

检查返回值、具体 `JobParameters` 与 `jobFinished` 是否对应本次运行。`onStartJob(true)` 表示本次仍有工作，之后按该次运行的完成协议收尾；`onStopJob(true)` 是请求重新调度，不是允许当前任务继续。收到停止时无论返回值如何都须停止本次工作，不能依赖稍后的 `jobFinished` 完成已停止任务，也不能让旧 worker 把结果提交到新一代任务。两个回调都须及时返回；通知期限与整个任务执行期限独立核对。

**确认与反证**：Android 14 的 target 行为文档明确，target API 34 及以上的 Job 回调超时可触发显式 ANR；低 target 的静默停止也不是成功。前台服务未及时提升可能是 `ForegroundServiceDidNotStartInTimeException` 崩溃；`shortService` 超时未停与其他限时类型的失败形式也有区别，不能统称执行 Service ANR。

**最小修复**：缩短 main 回调，耗时工作在可取消且归属清楚的任务内运行；停止回调只触发停止并及时返回，资源最终清理由明确所有者承担。要求的前台提升/Job 通知不要等业务网络调用；不通过虚报完成或吞掉取消隐藏超时。

**区分性验证**：受控堵住 main 的前序组件与回调自身依赖各测一次；worker 未完成时触发停止，验证回调返回、取消、资源释放与旧结果拒绝。分别记录 ANR subject、崩溃异常或 Job 停止原因，不能用“进程结束了”代替分类。

## 证据与交付边界

保留触发事件到完成信号的时间线、所有相关线程栈与进程对应关系；Perfetto 同看调度、Binder 流和锁持有者。`nativePollOnce` 可能是晚采样或错选线程，广播异步任务仍需查 worker；没有焦点时补窗口状态，不能只找 main 上的业务栈。

报告使用“可达阻塞风险”“受控等待已复现”“设备上已捕获某类 ANR”区分证据强度。注明尚缺的远端实现、OEM 配置或设备验证；StrictMode 可发现部分主线程误用，不能独立证明所有期限满足。保持同设备/构建比较，覆盖正常、慢依赖、过载、取消和恢复。
