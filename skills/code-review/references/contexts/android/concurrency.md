# Android 线程、重入与任务竞争

本文件用于主线程、worker、Binder、回调与对象存活之间的并发审查。权限与 Binder 身份另按系统入口处理；这里要求写出实际读写者、状态提交点和等待关系，不以“线程安全”“避免死锁”作为结论。

## 先标注每个入口真实在哪条线程运行

**进入条件**：共享字段、执行器/Handler/dispatcher、AIDL、Provider、listener、死亡通知或后台任务变化。

| 入口 | 必须核实的执行条件 |
|---|---|
| Activity/Service/Job 生命周期与 Provider 初始化 | 通常由进程 main 执行；Service 不是自动的新线程 |
| AIDL 本地直接调用 | 在调用者线程执行；本地 `oneway` 也不会自动异步 |
| AIDL 远端调用、Provider 数据访问 | 可能由多个 Binder 线程同时执行，不因同一个 service 实例而串行 |
| Binder 死亡通知 | 可从 Binder 线程到达；不能直接假定为 main |
| listener/异步结果 | 依据该 API 的 Handler/Executor 契约；自定义 Executor 还可能内联执行 |

给每个共享对象列 `创建/发布 → 读取者 → 修改者 → 关闭/释放者`，包含本地调用与测试替身。多进程各有内存副本，进程内锁不能维护跨进程唯一性；UI 对象的访问仍遵守其主线程契约。

## 可见性与复合状态同时成立

```text
main: 设置 account=A → submit(worker)
worker: 计算 A 的数据 → 写 cache/items
Binder: read cache/items              缺少共同同步就可能读到旧值/混合状态
main: 切 account=B ← worker A 晚到    即使字段可见，也可能提交到错误账户
```

检查发布与后续修改分别如何同步：同一锁、原子不可变快照或明确的单线程状态所有者。Executor 提交前的动作可先于任务执行，不代表提交后继续修改的集合也被保护；`volatile` 引用不会令集合元素或“检查后更新”整体原子。

```java
// 所有 writer 持同一锁构造独立不可变内容，再整体发布。
private volatile Snapshot current = Snapshot.empty();
void update(Result result) {
    synchronized (stateLock) {
        if (result.generation != activeGeneration) return;
        current = Snapshot.copyOf(activeAccount, result.items);
    }
}
Snapshot read() { return current; } // 一次读取得到同一代的完整快照
```

`Snapshot.copyOf` 必须隔离可变元素或约束其后续写入；writer 不能在发布后修改快照。若采用 main 串行所有权，Binder/worker 应发消息并异步取得结果，不能为了 confinement 又阻塞 main 或同步等待自身队列。

**确认与反证**：同字段存在可达并行读写且没有保证，或复合不变式跨多次独立操作，可报告静态竞争；不同线程名不自动说明访问重叠。全部访问受同一锁或在无重入的所有者队列执行时，不要求额外加锁。

**最小修复与验证**：选一种覆盖全部入口的所有权/同步协议，明确提交点；用两个闩锁固定“旧任务已读取输入→新账户已提交→旧任务才完成”，断言快照字段来自同一代且旧结果无副作用。顺序测试和仅增加 `volatile` 的测试不能覆盖复合竞争。

## 锁顺序、跨进程等待与回调重入

**进入条件**：锁内 IPC、外部 listener、同步等待、多个锁、native 非递归 mutex 或遍历中通知观察者。

```text
本进程: main 持 L1 → 等 worker；worker 持 L2 → 等 L1   需要证明可达同时持有
跨进程: A:T1 持 MA → 同步调用 B → 等 MB
        B:T2 持 MB → 同步调用 A → 等 MA              形成等待环
重入:   A:T1 更新一半 → 同步调用 B → B 回调 A:T1 → 读/改半状态
```

列出每条边的锁获取点、同步调用、回调目标及完成者。嵌套 Binder 事务可复用事务链中原来的线程；Java monitor 可重入时未必死锁，却可能观察半状态、修改正在遍历的集合；native 非递归 mutex 则可能同线程自锁。单 Binder worker 和 `void` 返回值都不能排除这些情形。

**确认与反证**：给出实际可达的相反持锁顺序、回调环或半状态观察，才把 API 共现提升为缺陷。仅有两个锁或两个 Binder 调用不等于存在环；不能把 Java 可重入锁的场景笼统描述为同锁必死锁。

**最小修复**：进程内建立可执行的锁顺序，缩短持锁；IPC/外部回调移出锁，先在锁内建立对重入有效的状态并捕获独立请求和版本，返回后重查版本再写回。依赖远端成功的结果不能提前提交。不能指望对端仓库永久遵守本地锁顺序，也不能只删锁。改 `oneway` 前先确认接口完成与失败协议。

**区分性验证**：用 barrier 让两个入口分别持住首个锁后走向第二条边；真实跨进程客户端在回调立即查询、取消或注销。断言有限时间内完成和状态完整；同时跑本地 Binder 直接调用验证重入。测试超时时收集全部参与线程，清理不能依赖已被堵住的队列。

## worker 饱和与同池 Future 等待

**进入条件**：固定池、池内再次 submit、同步 Future、阻塞桥接、共享 I/O/广播/回调执行器或线程数变化。

```text
pool(N): W1..WN 全在执行 parent → 每个 submit(child, 同一个 pool) → get(child)
queue:   C1..CN 等空 worker；空 worker 等 parent 结束      饥饿等待环
main/Binder: 等 parent → UI/IPC/广播 deadline 被进一步传递阻塞
```

从 Future 找到完成任务实际提交的池，再数需要同时空闲的 worker；协程中阻塞线程的 `get/runBlocking` 仍占容量。受限并行度与跨 dispatcher 的底层线程共享按实际库配置核实；不能仅因代码写了另一个 dispatcher 名字就证明容量隔离。

**确认与反证**：全部 worker 可进入等待且子任务只由同一池完成，可以静态证明饥饿风险；实际占满并收集等待栈后称已复现。子任务内联执行或由独立可推进的执行器完成时须重画关系，不能照搬同池结论。

**最小修复**：消除占着 worker 的同步子任务等待，使用完成链/异步组合；必要时隔离阻塞资源并限定入队容量。单纯扩大池只是推迟饱和；无界线程或队列可能把等待变成资源耗尽。取消/超时还要释放容量，不能只结束最外层 Future。

**区分性验证**：以闩锁让 N 个 parent 全部进入已知阶段后同时提交 child，检查队列、活跃数和完成状态；修复后同容量下 child 能推进。再验证慢依赖、取消及拒绝，断言无遗留任务/许可；不用增加 `sleep` 猜测 worker 是否已满。

## 注册、注销、死亡与旧一代回调

**进入条件**：服务连接、listener 注册、`linkToDeath/unlinkToDeath`、关闭重连或账户切换；注销与已排队回调可能交错。

```text
注册 remote A(g=7) → A 回调排队 → 注销 A → 注册 remote B(g=8)
→ A 的旧结果/死亡清理才执行 → 若只按业务 key 删除，会误删 B 或覆盖 B 状态
注册事务: 预留记录 → 锁外 link/register → 重查记录仍有效 → 提交/补偿
```

记录应携带 binder/token、generation 与 `REGISTERING/ACTIVE/CLOSED` 等实际需要的状态；完成、注销和死亡按同一协议决定谁清理一次。检查 link 时对端已死、注册成功但本地已取消、已排队应用消息和重复注销。`isBinderAlive()` 成功后仍可能马上死亡；不能把它当注册/调用成功保证。

**确认与反证**：证明旧通知能按复用 key 命中新记录，或部分注册失败丢掉清理责任。`unlinkToDeath` 成功的保证按 API 理解；它不能撤销应用自己此前另行 post 的消息。普通 listener 注销是否阻止在途调用须按各 API 契约，不把所有注销一律认为没有效果。

**最小修复**：状态提交和代号比较同锁/同所有者执行；旧回调仅能改变所属记录。外部注册/注销在锁外完成时保留预留与补偿路径，资源不能仅因 generation 不匹配就泄漏；死亡回调避免同步等 main。`binderDied(IBinder)` 是 API 34 新重载，旧版本按捕获 token 识别，不能无条件调用新 API。

**区分性验证**：受控拦住 A 的消息，完成注销与 B 注册后释放 A；断言 B 存活且 A 资源只清理一次。另测注册中杀远端、link 抛错、关闭与完成同时到达；远端死亡使用真实独立进程，单进程 mock 无法证明 Binder 死亡语义。

## 队列压力与完成协议

**进入条件**：频繁 Handler post、Flow/channel 缓冲、每事件一次任务、oneway 调用、重试或过载策略变化。

画 `生产速率 → 队列容量/每项保留数据 → 消费并行数 → 慢依赖 → 完成/拒绝`；main 快速投递也可能积压旧 UI 消息和大对象。远端同一 Binder node 的 oneway 事务有串行语义，但不同 node、同步调用混入和应用二次投递不能视为同一全局顺序。

**确认与反证**：持续生产能超过真实消费/保留上界，或丢弃让等待者永不完成，才报告相应缺陷。输入确有共同上界时不机械要求新限流；oneway 返回不能证明业务已执行、被接受或未来一定回调。

**最小修复**：按业务选择有界拒绝、可合并的最新状态或持久队列，明确用户看到什么。审查 `CallerRunsPolicy` 是否把阻塞任务推回 main/Binder；丢弃策略是否通知完成者；重要命令不能按可丢弃 UI 刷新处理。

**区分性验证**：可控暂停消费者后突发提交到容量边界，断言内存/队列上界、提交线程耗时、拒绝结果和恢复顺序；释放后验证必要命令完整、可合并事件只呈现允许状态。随机压力可补充，不能替代闩锁构造竞争窗口与状态断言。
