# Android BPF 代码审查

用于 Android 平台 BPF 程序及其 loader、Map 和网络消费者的变更。先按 [内核 BPF](../kernel/bpf.md) 检查程序本身，本页补 Android 的高频网络路径、策略/计费和交付边界。
审查从改动可达的坏路径出发，不要求先整理整个平台架构；仅改包处理时，不全量审计 APEX 和启动脚本。普通 App 不默认拥有加载、attach 或任意 Map 访问权限。

## 先找高频路径上新增了什么工作

拿到真实 hook、调用者和变更前后的常走分支，区分每包、每 socket、每次策略更新和启动一次的工作。同样的 helper 放在逐包路径与初始化路径，优先级不同。

- 对 cgroup/TC、tethering/offload 和高频 tracing，沿分支数出 helper/Map 操作及循环次数；继续追被内联的函数，不能只数源码里可见的调用点。
- 将最坏合法输入带入：小包高 PPS、双向并发、活跃 UID/连接多、Map churn、非线性/GSO skb、消费者变慢；不要只看大包单流的 Mbps。
- 写清新增工作量，例如 `每包 N 次查表 × 实际 hook 触发率`，以及循环是否随包、规则或扩展头数量放大；verifier 可接受的有界循环仍可能超出热路径预算。
- 静态即可证明的无用重复工作直接指出；具体增加多少 CPU、时延或功耗需要目标数据，不能编造固定 helper 单价或“超过几次就是滥用”的门槛。

## 检查 helper 和 Map 是否做了无用或过早的工作

| 看到的改动 | 实际审查动作与可操作结论 |
|---|---|
| 同一路径对相同 key 重复 lookup，或循环里反复读取不变配置 | 检查 key/Map 是否相同、两次读取间是否会改变状态、业务是否要求看到新值、指针是否仍有效。允许同次调用快照且结果只需读取一次时，复用局部结果；不能把可变策略跨包缓存，也不能因调用同名 helper 就合并。 |
| 新增一次 lookup/update，却只服务不会执行的功能分支 | 从已安全取得的协议、方向或配置条件证明该分支无需这些结果，再把无副作用的前置筛选提前；必需授权、配额和记账不能随“早返回”被跳过。 |
| 规则/包解析循环中调用 helper 或输出事件 | 构造让循环走满且每轮命中的合法输入，核对是否重复取同一数据、是否能只处理相关条目；缩小到实际所需工作，保留每条规则的语义和错误处理。不能只靠 unroll 把成本藏进指令数。 |
| 把共享计数改成 per-CPU，或为所有 Map 加锁 | 先确认竞争是否是根因，再检查读者汇总、possible CPU 内存、快照要求和更新频率；策略表或精确配额不能为性能直接改成互相独立的状态。 |

确认性能问题时指出哪类正常流量必经冗余操作、旧路径做几次、新路径做几次及结果为何相同。未命中后用 `BPF_NOEXIST` 建项再 lookup，可能是在处理并发建项并取得 value，不能当重复查询删除；必要的当前状态查询、不同 key 的查表和受控采样也不因“helper 多”报错。
回归至少包含不需要该功能的流量和确实需要它的流量：前者不再做无用工作，后者策略、计费和失败行为不变。只测“优化后能通网”不足以证明修复。

## 检查全包处理、事件输出和慢路径退化

- 只读少量包头却每包 `bpf_skb_pull_data(ctx, ctx->len)`，先核对是否无谓要求整个 skb 可写/线性；代价受 clone、非线性和目标实现影响。按需读取或仅准备所需范围，不能删除必要的边界检查或写前准备。
- `bpf_skb_pull_data(ctx, 0)` 不等于“拉整个包”：目标实现可能为当前线性头解除共享；直接写包的编译/加载路径也可能插入准备操作。结合生成对象和实际 helper 契约判断，不能仅靠源码调用次数下结论。
- 重复 `load_bytes`、`store_bytes`、checksum/调整头操作时，核对是否能合并同一所需范围和一次最终更新；不为减少 helper 扩大拷贝到全包，改写后仍须保留正确 checksum、offload 元数据并重建失效指针。
- 逐包 `trace_printk`、堆栈/字符串采集、ringbuf/perf 输出即使用户态没有消费也可能已在生产端花费成本；采样/过滤应在不必要的采集和记录构造之前。不能只在 Java 消费者丢弃事件后声称降低了 BPF 开销。
- 观测用途优先按需聚合、限频和有界丢失计数；精确计费与必要安全审计不能未经契约允许就采样。保留加载/attach 失败、降级与恢复的必要证据，不靠逐包 payload 排障。
- 修改 offload 支持条件或返回码后，检查正常流量是否大量落回 core stack；局部程序跑得更快，但有效 offload 比例下降、系统 CPU 上升，仍可能是退化。按路径区分必要 punt 与意外 fallback，不能为追求 offload 强行处理不支持的包。

验证需区分小包 PPS/CPU、吞吐/丢包/时延与观测丢失；涉及移动设备功耗时另取受控持续负载数据。对 clone、非线性 skb、GRO/GSO 和正常/异常分支分别比较，不能把所有差异都归因于 helper 调用开销。

## 性能修复不能改变策略和计费

**触发**：提前 return、减少查表/记账、调整 Map 类型、更新顺序、返回值、NAT/redirect 或统计读取清空。

- 按真实 program/attach type 推导 allow/deny、TC punt/redirect 与 xt_bpf 返回语义；包路径与 socket-create 路径分开。统计缺失不自动丢业务包，必要防火墙缺失也不自动放行。
- 检查 UID 与 appId、socket cookie、netId、ifindex 的实际 key 域及生命周期；卸载、多用户、socket/网络/接口删除与编号复用后，旧项和迟到事件不能把规则、tag 或计费归给新主体。
- 对共享 value 原地计数写最短跨 CPU 交错，检查丢增量；“lookup 后写回”不构成原子事务。单字段原子和 per-CPU 均不能自动保证多字段快照或全局精确限额。
- 核对 bytes/packets 的方向、L2/L3 单位、GRO/GSO 估算、端序、CLAT 与 tethering 路径；提前筛选不得漏记原合同要求统计的流量，不强制每个 hook 支持所有协议。
- A/B 统计 Map 的切换先查实际发布及 RCU 同步，再检查 inactive Map 读取/清空；只交换 Java 引用或锁住用户态读者不能阻止内核写者。
- 重定向或改写已发生后再失败，检查还能否安全 punt；缺 helper/Map、verifier/attach 失败与部分初始化分别追到必需阻断或可选降级，不能统一吞错。

确认时给出具体输入/并发时序和错误的策略归属、计数或包行为；已有兼容变体、允许近似统计及正确慢路径是反证。回归断言计数守恒、撤权有效和失败策略，并覆盖优化分支之外的流量。

## Map 布局与更新要同时检查旧消费者

**触发**：key/value 字段、默认值、容量/flags、pin 路径或编解码变化。

- 将 BPF 与 Java/C++/Rust 端逐字段对应到宽度、signedness、padding、alignment、端序和单位；类型/尺寸检查不证明字段含义相同。
- 同 boot 复用旧 pin 时，用一条真实旧格式记录按新声明解码。同尺寸字段交换仍可能把旧 `enabled=0` 读成非零；两端同步换头文件也不能转换已经存在的旧字节。
- 对平台、APEX 和 vendor 分别更新，只检查产品支持的旧/新组合；确需变化时保留旧协议或版本化 Map，并明确迁移、发布、失败和回滚顺序。不能靠清空共享状态回避兼容。
- 多字段/多 Map 更新查全部写者及内核读路径，失败半更新须满足策略和统计合同；不能只审查持有用户态锁的一个调用点。

回归使用旧布局样本、旧/新读写者和中途失败，断言原有禁用/启用及统计含义保留。仅新对象启动、`sizeof` 相等或新结构 round-trip 不能捕获旧字节误解。

## 权限变化要追到真实写入者

- 路径、owner/mode、SELinux label、共享标志或消费者变化时，分别查父目录 search、pin 文件 DAC、取得 FD、Map read/write 及程序 run/attach；路径可打开不等于能写 Map，已有/转交的 FD 也进入能力边界。
- loader 可能先在另一目录创建再 rename；最终目录名不能单独证明 label。“readonly”命名与 UID=root 也不能代替有效策略。
- 服务获准写 Map，不等于其任意 Binder 调用者获准改变规则；同 UID/shared UID 不能区分不同包或业务对象。确认必须给出未授权主体→服务入口/FD→具体策略修改的路径。
- 用真实服务身份验证合法访问，以未批准 UID/domain 和只读 FD 验证写失败且状态不变；不能为消除 AVC 给普通 App 全局 bpffs 写权限、放宽 neverallow 或关闭 enforcing。

## 构建、load 和 attach 只追本次受影响的边

- 修改 Android.bp、元数据、名称/section、APEX/init 或路径时，追到产品实际 `.o`、安装位置、loader 选择和消费者；编译成功不证明交付或加载。目标 manifest/config 与真实 loader 优先，不按 Android 版本号假定固定目录或 libbpf/CO-RE 能力。
- 对新增/移动程序分别证明 load、pin、attach 和必要 Map 初始化；loaded 属性可能只承诺一个阶段，不能拿它证明功能全部生效，也不能要求已有完整初始化的消费者提前兑现承诺。
- cgroup、TC、iptables/xt_bpf 和 tracepoint 查实际执行 attach 的拥有者、目标、方向和清理。上传/下载方向以真实接口与包流向判断；其他组件已正确挂载时，不报“loader 没 attach”。
- 追接口晚出现/删除、upstream 切换、重复 attach 与部分失败；修复不能覆盖其他拥有者或留下无人管理的挂载。失败沿 init/等待者传播时，不把提前发布 ready、关闭 reboot 策略或延长 Watchdog 当修复。

验证要有缺失对象、版本门控、错误 attach 和初始化失败；断言错误可见且必需策略不被绕过，再用受控真实流量验证目标 hook 生效。pin/程序 ID 存在与 mock 成功均不能替代行为断言。

## 重启和同 boot 更新检查遗留状态

服务退出不等于 pin/attach 消失，unlink pin 也不保证现有 FD 或挂载释放；pin 不跨整机重启持久保存。先确认产品是否支持同 boot 更新，再检查旧 pin、旧程序、缓存 FD、初始化默认值和并发消费者。
复用 Map 的 loader 不一定重设 chmod/chown，复用程序也不保证替换内容；按真实复用分支确认。不要将 oneshot loader 当热更新接口，或让客户端每次重连清空全局 Map。
回归分别覆盖进程重启、重复初始化、更新中断和受支持回滚；明确停写、迁移/重建、FD/attach 回收和重新发布顺序，检查短暂默认规则及统计基线。

## 交付能支撑结论的验证

从目标分支的 TEST_MAPPING、构建定义和测试断言选择最小相关检查，不要求按历史测试名跑整套 CTS/VTS。性能变更同时检查功能和成本，按同一目标/输入比较，记录未验证层次。
普通 `TEST_RUN` 也可能修改引用的 Map；使用独立对象/Map 或已获准的隔离环境。真实 load/attach、重跑生产 loader、刷机、改 SELinux 和重启设备不是默认只读 Review 动作。
报告写清“哪个高频分支增加了什么工作/破坏了哪项合同→可达后果→最小修复→区分用例”，分别标注静态充分证据、已运行结果与待测 CPU/功耗数据；不把缺压测当作明显无用重复工作的免责理由，也不声称已测出未执行的退化。
