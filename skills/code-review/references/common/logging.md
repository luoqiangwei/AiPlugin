# 日志覆盖、级别与诊断

日志审查看必要事件是否可诊断、严重度是否表达真实后果，以及记录本身是否引入泄漏或资源问题。按本次变更进入检查；不要求每个函数、每次成功调用都打印，也不把措辞、语言或个人格式偏好当作缺陷。以下示例为伪代码，具体 API、级别与字段服从仓库约定。

## 从行为分支发现缺失日志

**进入条件**：新增或改变持久化、注册/注销、初始化、恢复、后台任务、错误转换、重试、降级、安全决策或日志配置。即使改动中没有 logger 调用，也要检查。

1. 沿改动列出成功、失败、降级、恢复、取消、拒绝分支，标出操作阶段、业务最终结果和谁还能观察到结果。先看控制流，再搜索已有日志。
2. 对每个分支问：若只看生产允许保留的证据，能否区分“未执行、执行失败、部分完成、仍在重试、已经恢复”？错误返回给调用者不一定留下运维证据。
3. 对必须可诊断的事件追到实际记录者，核对生产级别、过滤、采样、关联上下文和输出通道。开发控制台出现过不证明线上可见，抛出异常也不证明已被记录。
4. 只有事件确有诊断/审计需求、现有证据不能覆盖且有实际影响时，才报告日志缺失；说明故障时会失去哪项定位或恢复依据。

诊断需求也可由关键操作和故障恢复过程推导，不要求项目先有单独的日志规范。若原因在异常转换、异步交接或回退后不可恢复，且缺失会妨碍定位、恢复或审计，应明确指出缺少的证据与负责记录的边界。

| 分支或状态 | 应寻找的必要证据与适用边界 |
|---|---|
| 重要失败被吞掉、转为空值/状态码或默认结果 | 失败原因、阶段和降级结果有记录者；真正无害且预期的探测失败不必升级为告警 |
| 异步、回调、定时或脱离请求的任务 | 重要失败能传回可靠拥有者或被记录；只创建 Future、提交成功或返回请求不覆盖任务最终失败 |
| 关键持久化、注册和恢复状态 | 需要据此定位丢写、未注册、恢复不完整时，能区分开始、提交/生效和失败；不要求每条普通写入打印成功日志 |
| 进入降级、持续不可用和恢复 | 可判断何时转入何状态及其原因；成功 fallback 不应伪装为原操作成功，恢复证据不能只剩失败计数 |
| 必要安全审计 | 按项目契约覆盖认证/授权决策、高权限操作、关键配置或敏感导出等结果；日志级别与审计是否必留分别判断 |
| 取消或普通校验拒绝 | 可按诊断需要记录受控结果；预期取消、正常业务拒绝本身不构成系统故障，也不自动要求逐条记录 |

指标可说明失败率，调用链可提供时序，审计可提供归属；能可靠满足本次具体诊断需求时可以作为反证。聚合计数无法单独解释某次关键持久化为何失败，抽样链路也不能自动替代必须保留的审计。

## 确认日志拥有者与传播边界

为同一个最终失败找拥有足够业务上下文、决定最终响应或恢复策略的记录者。底层保留错误及 cause，边界记录最终结果通常比每层 catch 打栈更清楚；不得机械规定所有异常只能有一条日志。

- 检查统一异常 handler、任务执行器、队列消费者和可靠审计是否实际覆盖该路径、字段与生产配置。覆盖成立时不要求业务层重复记录。
- `catch → 记录 → 原样抛出 → 上层再次打栈` 可能重复计算同一失败；若底层记录的是独立状态变化或不可重建的阶段信息，说明事件差别再保留。
- 转换、吞掉、默认降级、任务结果无人等待时，原来的上层拥有者可能已看不到错误；应在新责任边界补足证据或可靠传递，不能只删重复日志。
- 重抛时保留 cause；外层若只记“处理失败”且丢失底层错误分类，也不能视为充分覆盖。清理失败须和主失败关联，不能覆盖主失败。
- 异步边界核对关联上下文传递及清理，避免线程复用串入别的请求。任务已排队、已开始、已完成是不同结果，提交成功不能写成执行成功。

```text
风险：save() catch e { log.error(e); throw e }
      handler catch e { log.error(e); return failure }
修复形状：save() 保留 cause 并补充安全的阶段上下文；handler 记录最终失败。
反例：save() 已记录“补偿也失败”，handler 记录“请求最终失败”，可为不同事件；
      用关联 ID 区分，不能以“多于一条”直接删掉补偿失败证据。
```

## 按结果与处置意图判断级别

先读仓库级别规范、告警查询和生产阈值。下面是常见意图，不是跨框架强制映射；框架没有 FATAL 时按其 CRITICAL/ERROR 等真实语义判断。级别高不代表更有价值，安全事件也不一律是 ERROR。

| 级别 | 判断条件 | 常见误用 |
|---|---|---|
| TRACE / VERBOSE | 临时深挖才需要的逐步、逐项或高频细节，开关和数量须受控 | 生产默认开启并输出每帧、每包或每次函数进出，挤掉关键事件或拖慢热路径 |
| DEBUG | 排查才需要的细节、可控的重试过程或局部状态 | 把必须留存的最终失败只放在生产关闭的 DEBUG |
| INFO | 有诊断价值的正常生命周期、关键状态生效或恢复 | 高频逐项成功、循环进度淹没状态变化；尚未提交就报成功 |
| WARN | 偏离正常预期、发生降级或存在需关注的风险，操作仍可继续 | 正常缓存未命中、普通校验失败、用户主动取消都打 WARN |
| ERROR | 操作最终未完成承诺，或发生需要调查的非预期故障 | 已按契约取消/拒绝、可恢复的每次重试都打 ERROR 和完整栈 |
| FATAL | 服务/进程已无法继续，或即将因不可恢复状态终止 | 单个请求失败却进程健康；假定调用 fatal 一定会退出进程 |

重试过程和最终结果分别判断：预算内暂时失败可记受控细节；预算耗尽、不可重试或承诺已破坏时保留最终失败。达到重试次数不必然是 ERROR，若有效降级正是契约，按其影响记录降级；恢复时按状态变化记录，避免每次健康探测都刷“恢复”。

普通格式校验、资源不存在和取消先按业务契约归类。若取消暴露资源未释放、拒绝发生在越权写入之后，真正异常是后续破坏的事实，不能靠降低级别掩盖。必要拒绝审计可独立留存，严重度仍依据上下文。

## 信息够用且可以安全保留

对必要事件检查：**操作、阶段、结果、错误分类/异常 cause、受控关联 ID、允许的状态上下文**是否足以定位。时间、组件、版本等已有框架字段不必重复拼进消息；恢复事件关联此前故障，业务状态不能只写含糊的“失败了”。

- 事件名/消息模板保持稳定，动态值使用结构字段或参数。错误对象经已验证的脱敏与编码策略保留诊断所需的 cause；只有 `e.message` 可能丢链路，无条件原样打栈也可能泄漏。
- 关联 ID 使用服务生成或校验过长度、字符集和来源的值；追踪 ID 不作为授权证据。跨任务要传递，离开作用域要清理；没有请求的后台任务可用受控任务/运行 ID。
- 状态上下文只收集定位所需的枚举、阶段、次数、受控对象标识等。禁止凭据、token、密钥和不必要的个人数据；请求体、URL 查询、连接串及异常消息可能暗含这些值。
- 验证实际编码器、采集与展示如何处理换行、分隔符和控制字符。参数化本身不阻止伪造多条日志；限制字段及总事件大小，安全替换畸形字段并保留必要事件。
- 不把未受控的原始输入、用户标识或异常全文用作动态事件名、字段名或无界的限流/去重键。经批准的主体或关联标识可以作为受保护、可检索的字段值；其索引、聚合和保留状态须有容量与隐私预算，不能一概禁止关联，也不能把高基数值无界展开为标签集合。
- 异常栈放在有访问控制且允许保存的通道；核对生产与客户端输出边界，避免 `printStackTrace`、调试响应或未经脱敏的日志导出泄漏内部信息。

```text
风险：catch e { return [] }                  // 数据库失败被误认为没有记录
修复形状：向拥有者传递带 cause 的查询失败；若契约允许返回缓存，记录
          operation=query, phase=read, result=degraded, reason=db_unavailable,
          correlation_id=validatedId, cause=approvedDiagnostic(e)
反证：可靠统一 handler 已记录该失败并产生真实失败响应；无需查询层再打一次。
风险：log.error("login " + rawRequest + e)    // 普通拒绝、敏感值与伪造换行混在一起
修复形状：按契约留认证拒绝审计，记录稳定事件名、受控原因与关联 ID；
          仅包含获准主体标识，编码并限长；按实际风险选级别，不保存口令或请求体。
```

`approvedDiagnostic` 代表仓库已验证的安全输出策略，不是伪造一个函数名就证明脱敏；检查真实实现、嵌套 cause、堆栈和采集器最终产物。

## 控制日志成本与失效方式

沿热路径估算 `事件频率 × 单条大小 × 格式化/栈捕获/输出成本`。级别关闭不证明零成本：参数求值、序列化、数据库查询和对象 `toString` 可能已发生。按框架使用延迟参数、supplier 或有效级别保护，并检查过滤发生在哪一步；不凭少量拼接就认定性能缺陷。

循环、轮询、攻击可触发拒绝和重试失败应核对采样、限流、聚合与去重。范围和保留状态要有界，汇总能体现次数与时间窗；不能把一次依赖故障放大成每请求每层的完整栈风暴，也不能让最终失败、必要审计或恢复的全部证据被过滤掉。

异步队列还要核对容量、满队列策略、阻塞线程、关机排空和丢弃可观测性；换异步 logger 不消除持续输出超过 sink 吞吐的问题。业务关键线程不应因普通诊断日志的网络/磁盘故障无限等待或异常退出；日志失败的报告避免递归写回同一坏通道。

普通诊断日志的 sink 故障通常应隔离，并有受控丢弃/备用通道和健康信号。若审计可靠性属于操作成功条件，按真实契约检查持久化、拒绝/阻塞或补偿，不能一律“日志失败就丢弃继续”，也不能擅自将所有日志升级为业务事务。

## 用有区分力的验证排除误报

选择本次改动可达的代表性分支，经过实际拥有者和生产相关过滤/编码配置捕获输出。日志调用 mock 只证明调用发生，不证明最后能安全检索；低风险文字调整不强制增加测试。

| 验证场景 | 应有的区分性结果 |
|---|---|
| 重要失败被转换、吞掉或发生在后台 | 最终失败/降级可查询，带阶段、结果、cause 与关联；成功场景不产生同样失败事件 |
| 底层失败经统一 handler | 同一最终失败不会每层重复打栈；不同补偿失败仍能区分，且不因去重失去唯一证据 |
| 先短暂失败后成功、耗尽预算、降级后恢复 | 中间过程数量受控，最终失败或真实恢复仍保留；日志结果与业务实际状态一致 |
| 正常校验、取消、业务拒绝与非预期故障 | 前者不污染系统 ERROR 告警，必要审计仍存在；后者在生产阈值下可见 |
| 带凭据/个人数据/嵌套异常和 CR/LF 的输入 | 捕获最终序列化记录，敏感值不出现，不能伪造额外事件，大小受限且必要事件未整体丢失 |
| 高频失败、关闭低级别和不同关联 ID | 输出量、构造开销及去重内存有界，关键证据仍可查；不只测单次 logger 调用 |
| sink 不可达、磁盘满、队列满与关机 | 普通业务按契约运行、日志失效可察觉；强审计操作满足其明确的失败/交付保证 |

**确认条件**：说明具体分支、实际记录者/配置、丢失或错误的信号，以及故障诊断、告警、资源或数据暴露的后果。只有缺少一条自认为好看的日志、偏爱某个词或已有可靠覆盖，不构成 finding。
