# 通用代码审查要点

本文件把设计、重构、契约、所有权、并发与测试原则变成推导步骤。按改动读取相关规则；不要求为了符合某种设计风格重写项目。所有代码均为原创的简化审查示例。

## 输入校验与状态约束

**进入条件**：新增输入、构造器、setter、持久化映射、反序列化或状态转换。

1. 写出合法值域和状态转换，例如 `units > 0`、`start <= end`、`PAID 不可再次扣款`。区分格式合法与当前主体有权操作。
2. 搜索全部构造与修改入口，包含 ORM、builder、反射、恢复和内部调用；只在 Controller 校验不能证明其他入口安全。
3. 依次检查廉价的大小/数量限制、可解析性、领域约束；身份可先取得时先限制其资源权限。校验前的解压、递归或正则也可能先耗尽资源。
4. 检查成功创建后是否仍能通过共享引用或公开 setter 破坏约束；“构造时检查过”仅在约束持续被维护时成立。

```text
风险：job.units = raw.units; reserve(job); if units <= 0 then reject
改法：units = parseAndValidateUnits(raw.units); job = createJob(units); reserve(job)
```

**确认条件**：存在可达入口接受非法值，并让该值参与操作或逃逸成为有效对象。**反证**：输入模型已有不可绕过的构造约束，且之后没有可变别名破坏它；无需要求各层重复同一格式校验。

**验证**：边界内/边界上/边界外；至少一条非 UI 调用路径；失败时未产生保留记录或其他副作用。验证工厂不替代对象/租户授权。

## 失败原子性

**进入条件**：一次操作改变多个字段/记录/资源，或包含回调、外部系统和可能失败的步骤。

按执行顺序列出效果，在每个失败点截断：`验证 → 修改 A → 修改 B → 发事件 → 返回`。对每个前缀说明调用者看见什么、能否安全重试、由谁恢复。不要把“函数抛异常”当成“副作用已回滚”。

```text
风险：delete(old); next = build(raw)       // build 失败后旧状态已丢失
改法：next = buildAndValidate(raw); replaceAtomically(old, next)
```

替换原子性须由实际机制证明，如同一临界区、数据库事务或支持该语义的文件操作；本地变量交换不自动覆盖持久化和远程系统。多个系统不能共享提交时，按契约选择持久化待办、幂等、补偿或向调用者暴露处理中状态，不强制所有系统使用同一模式。

**反证**：契约明确允许部分成功，返回结果逐项描述，且重试不会重复已完成动作；这不是原子性缺陷。**验证**：对每一步注入失败，检查旧状态/已提交状态、事件和重试次数；失败前后都不出现无法解释的中间状态。

## 对象所有权与可变数据

**进入条件**：保存调用者对象、返回集合/数组、缓存实体、以可变对象作 hash key、跨线程共享快照。

画出引用关系，追踪修改能力而不是变量修饰符：`调用方 → 原对象 ← 被审对象 → getter`。`final` 只固定引用；只读包装可能仍映射到可变原集合；浅拷贝只隔离容器，元素可能继续共享。

```java
// 风险：构造后外部可修改内部状态，getter 又暴露同一数组。
this.deadlines = supplied;
long[] deadlines() { return deadlines; }

// 在契约需要独立数组快照时，两个方向都隔离。
this.deadlines = supplied.clone();
long[] deadlines() { return deadlines.clone(); }
```

接着检查内容：对象数组仍需按元素的可变性决定策略；合法的所有权转移、受同一锁保护的共享视图或已不可变元素，不应无条件深拷贝。以对象作为 map/set key 时，`equals/hashCode` 所依赖的字段在存储期改变，可能令元素无法查回；先追踪实际变更路径再报告。

**验证**：构造后修改输入；修改 getter 结果；修改嵌套元素；验证快照和 key 查找契约。性能成本大的复制需要结合所有权约定选择，不机械要求到处 clone。

## 类型安全

**进入条件**：外部数据解码、类型转换、异构存储、反射、FFI 或其他表示边界。

沿 `输入 → 解析/转换 → 保存 → 读取/使用` 追踪值，说明在哪一步建立了所需的类型与表示保证。区分代码中的类型声明、真实运行值和业务约束；不能只看最终抛错位置，也不能把某一种语言的类型擦除或强转语义推广到所有语言。

按语言规则判断哪些条件由编译器或运行时维护，哪些被断言、未检查转换或外部调用绕过。正确封装可能在边界一次验证后向内部提供可信类型；不要求每层重复验证。Java 泛型、TypeScript 类型断言和 Rust unsafe 的具体证明义务分别读语言模块。

**确认条件**：可达输入突破所需的表示或类型约束，并造成崩溃、错误计算或业务分类错误。**修复**：在真实信任边界建立保证，而非只修改声明或压制告警。**验证**：正常值、错误类型与边界值经过真实转换后满足契约；没有破坏路径时不把所有转换都报错。

## 接口设计与封装

**进入条件**：新增公共接口、工具层、配置参数、拆类/拆方法或多处相同调用序列。

找出调用者为正确使用接口必须知道的内部知识：是否先锁再刷新？是否某个 flag 与某状态必须配对？是否取得 buffer 后必须手动更新三个索引？再搜索调用者，找已有的次序/配对差异。

```text
风险接口：beginEdit(); setPayload(x); updateLength(); updateChecksum(); endEdit()
可收敛为：replacePayload(validatedPayload)
```

只有这些步骤确实属于同一不变式时才收敛；若分步接口用于受控批处理且有有效状态机，它可能是正确设计。函数短不表示抽象好，函数长也不表示有缺陷。定位到漏更新 checksum、异常后未解锁等实际错误才形成 finding；仅有未来误用可能时给非阻断建议。

**验证**：所有公开操作序列保持对象有效；异常路径能退出编辑状态；正常批处理能力和成本不退化。说明接口减少了哪项必须由调用者记住的责任。

## 重复代码与业务规则

**进入条件**：重复校验、多个派生字段、分散常量、同一计算在不同入口实现，或为去重引入通用框架。

问“哪条需求改变时，这两段代码必须一起改？”若答案是同一个业务知识，定位唯一权威定义或自动生成关系；若各自服务不同规则，保留独立入口。复制内容不同也可能重复知识，例如缓存的 `total` 与可独立修改的 `items` 必须同步。

```text
同一规则分叉：interactiveUpload.limit = 8; backgroundUpload.limit = 16
先确认：二者是否承诺同一账户额度？若是，查漏改导致的可观察差异。
偶然相似：downloadRetryBudget = 3; approvalQuorum = 3
二者变化理由不同，不因当前数值一致而抽成 SHARED_THREE。
```

**反证**：显式缓存具有统一更新/失效机制；为独立业务演进保留的相似代码；边界安全校验与 UI 提示并非必须消灭的重复。**验证**：选一个规则变化样例检查各入口一致；确认新抽象没有隐藏条件分支、循环依赖或跨业务耦合。

## 并发与同步

**进入条件**：共享可变状态、检查后修改、缓存发布、锁外回调、引用计数与释放。

```text
契约：最多允许一个正在运行的任务。
A: read active=0 → 通过检查
B: read active=0 → 通过检查
A: active++ → start
B: active++ → start             // active=2，契约破坏
```

检查与更新要属于同一正确的原子操作，不能只把 `active++` 换成原子自增。然后分别证明：谁能看见初始化后的状态、谁阻止并发修改、谁保证对象使用结束前不释放。这三件事可由不同机制完成，不能以“有锁/有 Arc/用了 RCU”代替证明。

**反证**：入口被同一事件循环串行化且无重入/跨线程访问；整个条件更新受同一锁/数据库原子操作保护。不要要求单线程私有数据加锁。

**修复验证**：明确线性化点/事务提交点；用 barrier/latch 或受控调度让两个执行者到达同一竞争窗口。随机压力无告警只作补充；避免仅靠 sleep 碰运气。跨进程/多实例的不变式不能只靠进程内锁保证。

## 异步任务、取消与资源释放

**进入条件**：线程池、协程、队列、回调、超时、重试、关闭和取消。

1. 追踪提交速率、并行数、队列容量、单任务保留数据、排队时间和拒绝行为。固定 worker 数量不能证明队列有界。
2. 在每个等待点取消：是否已经扣配额/移出消息/持有锁？Future 被丢弃后谁负责剩余工作？远端是否可能已经提交？
3. 追踪身份、租户、追踪与事务上下文在线程/任务边界的传递，不能假定 ThreadLocal、Binder identity 或请求对象自动延续。
4. 关闭时先停止接收，再处理或取消已有工作，最后释放资源；回调仍可能重入或重新提交时需证明终止条件。

**确认条件**：实际入口可制造超出预算的积压、取消后丢失必要动作或资源、重复远端副作用、关闭后访问已释放对象。**反证**：上游容量、排队和生产者确有共同上界；同步锁的临界区短且不跨等待，不因存在 async 就要求更换锁。

**验证**：慢依赖+突发提交、队列满、等待中取消、完成与取消竞争、关闭后回调；检查资源总量与业务状态。修复可选背压/拒绝/容量隔离/幂等，必须解释过载时用户实际得到什么。

## 错误处理与恢复

**进入条件**：catch、默认值、重试、错误码转换、异步任务结果和日志。

沿错误返回到最终调用者，检查原本不同的状态是否被折叠为同一个值。权限服务失败返回 `true` 是失败放行；数据库失败返回空集合可能被误报“没有数据”；但推荐服务失败返回预定义默认项也可能正是有效降级。

判断重试时，先区分操作未执行、已执行但响应丢失和确定被拒绝；只有重复执行不会改变承诺时才可直接重试。对主要错误保留上下文，清理错误不能掩盖主失败；日志需能定位失败阶段，同时去除令牌和不必要的用户数据。

对被吞掉、转成默认值或脱离调用链的失败，反查谁负责记录最终结果；不能只检查现有日志的措辞。必要日志、级别、重复记录、限流和发布可见性按 [日志审查](logging.md) 判断。

**验证**：按变更实际可达的失败类型选择代表性用例，观察最终响应、副作用、日志和重试；不要求不存在的取消或部分写入路径。不能只证明“异常被 catch 了”。

## 测试有效性

**进入条件**：任何宣称修复缺陷或保持行为的改动，尤其测试新增、删除和重写。

先写一对区分性场景：一个满足业务前提应成功，一个只改变关键条件应失败。再思考删除关键检查、改错比较符、忽略第二次写入失败、重复发送事件时，断言能否检测；这是审查推演，不要求修改源码运行整套变异测试。

| 被审契约 | 有区分力的证据 | 不能独立证明它的测试 |
|---|---|---|
| 对象授权 | 同角色另一用户不能访问同一对象；合法拥有者仍可访问 | 只测匿名拒绝，或把服务 mock 为始终拒绝 |
| 失败原子性 | 中间步骤失败后数据库/资源与承诺一致 | 仅断言抛异常，未检查已发生副作用 |
| 并发最多一次 | 在竞争窗口重放并统计最终副作用 | 两次顺序调用或仅检查调用次数 mock |
| 代理/框架行为 | 经过真实代理、过滤器链或相应适配边界 | 直接 new 对象调用或外层测试事务 |
| 公开数据/ABI | 独立契约样本与旧客户端/格式互读 | 用同一段错误计算生成 expected 和 actual |

修复用例应能解释为什么旧行为失败、新行为通过；有环境条件时如实说明。单纯格式调整、低风险可逆改动不强制新增测试；沿用仓库有效门禁。

存量代码难以装入测试时，先找能替换外部客户端、I/O、时钟或随机源的现有边界，再确定由哪个参数/装配点选择替身。保持被测核心逻辑与生产相同，不在测试版本另写一套业务算法，也不为了测试把所有 private 状态公开。需要拆边界时先捕获相关可观察行为，小步调整；已确认的安全错误不能因被旧输出快照记录而变成必须保留的契约。

## 兼容性与演进

**进入条件**：改签名、返回顺序、默认值、错误码、序列化、数据库结构、构建条件或公开配置。

区分可以同步更新的内部调用者与无法控制升级节奏的公开调用者。列出实际需要支持的组合：旧调用者→新实现、新调用者→旧实现（确有滚动部署要求时）、升级后数据→回滚实现。反射、插件、脚本、持久化和跨分区接口也是调用者。

“纯重构”的通过条件是这些观察点行为不变，或已经明确将改变纳入需求。不能因为单仓全部编译通过就断言已覆盖外部调用者；也不能要求完全内部函数永远保持旧名字。

**修复验证**：兼容适配或分阶段迁移；使用独立旧格式样本、旧客户端和故障回滚演练。数据库与协议分别检查新字段默认、未知字段、顺序/布局和错误处理，不要求不存在需求的全版本矩阵。

## 性能与资源开销

**进入条件**：循环内 I/O/查询、解析与拷贝、主线程/事件循环工作、无界缓存和日志。

写出简化成本：`请求数 × 每请求任务数 × 单任务成本`；对嵌套循环、逐条查询和重复解析找输入如何放大成本。先确定输入上界、运行线程、并发和预算，再判断是否构成可用性或体验问题。

**确认条件**：实际规模下引入 N+1、超预算阻塞、无界保留或明显复杂度退化，并有查询次数、路径推导或可比测量支撑。小而有界的集合、短临界区、已有缓存命中不能套用最坏复杂度直接报高危。

**修复验证**：同数据/设备/构建条件对比必要指标，检查错误与过载路径；不要通过全局 EAGER、无限并发、关闭校验等方式把成本转移成更大问题。
