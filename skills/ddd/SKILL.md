# DDD

用于从需求到可运行、可测试、可交付系统的领域驱动设计。先判断项目和任务是否需要 DDD，再选择相关步骤。用户要求实现时，交付可验证的行为；用户只要求分析、设计、审查或单点修复时，完成相应范围。

## 执行原则

1. **先理解问题和约束**：业务项目先理解业务规则；平台项目先定位子系统、调用链和平台契约，再判断哪些规则值得领域建模。
2. **先打通再扩展**：优先完成一个核心用例的端到端垂直切片，再迭代其他用例；不要一次生成所有层的空壳。
3. **规则清晰，抽象适量**：确定主要组织方式、模块职责和依赖规则；Layered、Onion、Hexagonal、Clean、COLA 的原则可以重叠，但不重复搭建同义层。CQRS、Event Sourcing、BFF 和微服务分别按证据引入。
4. **以真实项目为准**：先检查现有代码、依赖、目录约定、构建和测试命令。参考材料以 Java/Spring Boot 为主，不得无条件照搬。
5. **按需读取资料**：只打开当前步骤需要的参考模块及其具体文件。本文件规定适用范围和默认决策；参考中的模板、人数阈值、旧等级名和框架示例不能覆盖这些规则。
6. **完成必须可验证**：实现时按改动影响运行项目规定的构建、相关测试和必要的实际场景验证。记录目标、命令和结果；环境不足时区分已实现、已验证和待验证，不把编译或模拟结果当成设备验收。
7. **能力按需启用**：聚合、Repository、持久化、数据库迁移、领域事件和 Outbox 都需要具体用途。没有使用的能力标注不适用，不为满足清单新增基础设施。

## 入口：识别项目和任务

先检查仓库说明、现有代码、构建文件、测试和运行方式，优先从项目证据补齐上下文，不把问题清单变成逐项采访。

| 项目或任务 | 执行路径 |
|---|---|
| 复杂业务规则、新业务模块或领域重构 | 使用下方主流程，按本次范围选择深度 |
| 简单 CRUD、配置、局部缺陷、性能或并发问题 | 直接定位、实现和回归；需要时补规则或状态表，不强制事件风暴、聚合设计和架构重选 |
| 已有项目中的功能或改造 | 先建立现状，沿已有扩展点完成最小可验收切片；结合下方存量分支 |

这些路径可以组合。新项目采用相关流程；已有项目从当前问题进入，发现规则或边界变化时再返回建模步骤。只有会影响正确性或验收的未知项才需要先澄清，其他假设显式记录并继续可独立推进的工作。

## DDD 项目开发主流程

```text
业务目标与约束
  → 按需事件风暴与统一语言
  → 限界上下文与上下文映射
  → 规则、状态与必要的聚合模型
  → 模块依赖与 CQRS / Event Sourcing 独立决策
  → 一个核心用例端到端打通
  → 按用例迭代扩展
  → 测试、架构审查与质量门禁
  → 交付、监控、文档和持续演进
```

### Step 1：明确业务目标、范围和约束

先回答以下问题：

- 系统服务哪些角色，最重要的 1～3 个业务场景是什么？
- 哪些业务规则、状态变化和异常分支构成真正的复杂度？
- 项目是新开发还是存量改造？现有痛点和期望收益是什么？
- 技术栈、团队规模、领域专家、交付周期、数据一致性、部署和合规约束是什么？

同时判断 DDD 是否适用。简单 CRUD、短期原型或缺少复杂规则时，选择更简单的实现。平台项目补充入口分流中的工程定位，不把技术层、进程或安装分区直接当成限界上下文。

**产出**：项目简报，包含目标用户、核心场景、业务约束、技术约束、成功标准、初步核心/支撑/通用子域，以及所有关键假设。

**进入下一步的条件**：核心场景能够用业务语言完整描述，并知道本次迭代不做什么。

### Step 2：用事件风暴梳理业务并建立统一语言

跨角色、跨系统或规则存在争议时，选取核心场景做事件风暴。小范围且规则清晰时，用简短的术语、状态转移与验收场景替代完整工作坊。

需要事件风暴时，按时间顺序梳理主流程和异常流程：

1. 用过去式记录领域事件，例如 `OrderPaid`。
2. 为事件补充触发命令、执行角色、业务规则和外部系统。
3. 标记流程转折点、争议点和尚未明确的规则，不用技术方案掩盖业务问题。
4. 汇总业务术语，确保后续模型、接口、代码和文档使用同一语言。

**产出**：

- 事件时间线：`顺序 | 角色 | 命令 | 领域事件 | 业务规则 | 异常/Hot Spot`。
- 统一语言表：`术语 | 业务含义 | 同义词 | 使用边界`。
- 热点清单和需要领域专家确认的问题。

**进入下一步的条件**：核心行为和术语清晰，异常流程及未决问题已显式记录。时间线上用于分析的事件不意味着必须实现事件总线或持久化事件。

### Step 3：划分限界上下文并设计协作关系

根据业务语言、规则一致性、数据所有权、团队职责和变化频率划分限界上下文，而不是按数据库表或技术层拆分。

为每个上下文明确：

- 业务职责、核心能力和拥有的数据。
- 核心/支撑/通用子域属性。
- 上游与下游依赖，以及同步调用、领域事件、防腐层等协作方式。
- 独立部署、扩缩容和团队自治是否真的有需求。

默认先形成清晰的逻辑模块。只有部署节奏、扩展需求或团队所有权确实不同，才进一步拆成微服务。限界上下文不必与服务、进程、构建模块或平台分区一一对应。

**产出**：上下文清单和上下文映射图，能够看出每个上下文的职责、模型所有权及集成关系。

**进入下一步的条件**：同一业务术语在不同上下文中的含义已澄清，数据归属和跨上下文一致性方式明确。

### Step 4：设计聚合和领域模型

优先设计核心上下文。先明确规则、不变式和状态转移；需要实体身份和一致性边界时再设计聚合，简单策略、算法或数据转换不必包装为聚合。对采用聚合的部分完成以下工作：

1. 区分实体和值对象，选择聚合根。
2. 按业务不变式确定一致性边界，不按照页面或表结构拼聚合。
3. 定义业务行为、状态转移、约束和异常路径。
4. 需要表达或订阅领域事实时，定义有业务意义的领域事件及触发条件，不要求每次状态变更都发布事件。
5. 需要保存和重建聚合时定义 Repository 接口；其他外部能力按需定义端口。只有不自然属于实体或值对象的领域规则才放入领域服务。

建议用下表形成可直接编码的模型：

| 上下文 | 规则/聚合 | 实体与值对象 | 关键不变式 | 业务行为 | 领域事件（如需） | 存储/端口（如需） |
|---|---|---|---|---|---|---|

**进入下一步的条件**：

- 使用事务和聚合时，原则上让事务与聚合一致性边界对齐；跨聚合通过 ID 引用。必要的例外记录理由，不能用最终一致性替代明确要求的原子性。
- 值对象不可变，实体包含业务行为而不是只有 getter/setter。
- 抽取出的独立领域核心不依赖 Web、ORM、消息框架等基础设施；平台适配代码遵循现有框架契约，不要求整个存量组件零框架依赖。
- 应用服务只编排用例，不抢走领域业务规则。

### Step 5：明确架构、读写模型与状态存储决策

存量项目优先沿用合理的模块和扩展点。新模块根据规则复杂度、依赖隔离、可测试性和实际技术栈选择主要组织方式；团队人数不直接决定架构：

- 简单分层或三层渐进改造：考虑 Layered。
- 多入口或外部实现替换需求明显：优先 Hexagonal。
- 需要领域居中的同心层与依赖倒置：考虑 Onion。
- UseCase 驱动和严格模块隔离：考虑 Clean。
- Java/Spring Boot 且需要 COLA 规范、扩展点和脚手架：考虑 COLA。

然后确定：

- 各层职责、允许依赖方向、包和模块结构。
- 领域对象、持久化对象、传输对象和视图对象的边界及转换位置。
- 事务、异常、鉴权、事件发布分别由哪一层负责。
- **读写模型**：默认共享模型；读写规则或视图确实分化时采用 CQRS。模型分离可以共享数据库，查询可直接读取适当的数据视图。
- **读写存储**：仅在负载、查询优化或隔离需求支持时拆分，明确同步机制、一致性要求与运维成本。
- **状态事实源**：独立评估当前状态存储或 Event Sourcing。事件溯源以事件作为事实源，不是 CQRS 的必经升级；普通审计日志不自动构成事件溯源需求。

**产出**：与范围相称的架构说明、模块与依赖规则、读写和状态存储决策；重要取舍记录备选方案、理由和影响的 ADR。参考资料中的 L0/L1/L2 和历史 L3 名称只帮助定位示例，不是行业统一等级或升级顺序。

**进入下一步的条件**：能解释选择理由，并通过现有构建边界、静态检查或适当的架构测试检查关键依赖；不为一次局部改动强制安装新的检查框架。

### Step 6：端到端实现一个核心用例

选择业务价值高且能代表领域复杂度的一个用例，例如“创建订单”，先打通完整垂直切片。不要先创建所有聚合、所有接口或所有空 Service。

按以下顺序推进：

1. **定义用例契约**：输入、输出、前置条件、成功结果、业务异常和验收场景。
2. **实现领域行为**：规则、不变式、状态转移及所需模型，验证关键行为和异常路径。
3. **实现应用用例**：沿项目现有结构编排对象和外部能力；使用事务时在完整用例边界协调，不让单个 Repository 提交破坏用例原子性。
4. **实现外部接入**：按需实现存储、协议适配和客户端；使用数据库且结构变化时提供迁移。只在隔离或替换有价值时新增端口。
5. **实现入口**：按真实接口完成参数校验、授权和错误处理；根据协议和重试语义设计 DTO、幂等或回调，不默认使用 REST。
6. **装配并真实运行**：通过实际 API、CLI、消息或设备入口验证成功与关键失败路径。

**产出**：一个可运行的核心用例、必要的数据库迁移、接口契约、分层测试和实际运行结果。

**进入下一步的条件**：核心场景已端到端验证，而不只是类已生成、模块能导入或项目能编译。

### Step 7：按业务用例迭代扩展

重复 Step 6，一次增加一个可验收用例：

- 优先补齐同一核心流程，再扩展其他上下文。
- 新业务规则优先落在领域模型，不堆进 Controller 或上帝 Service。
- 简单查询保持简单；只有读写模型确实分化时才引入 CQRS。
- 需要可靠事件投递时，选择与存储和协议匹配的机制。数据库状态与消息需原子提交时可用事务 Outbox，并验证重试和消费幂等；进程内通知或 Binder 回调不自动需要 Outbox、消息队列或死信。
- 业务理解变化时，先修正统一语言和模型，再调整代码，不让代码与业务术语分叉。

每个迭代都保持可构建、可测试、可部署，避免长时间停留在半成品架构改造中。

### Step 8：执行测试、代码审查和架构质量门禁

| 适用范围 | 验证内容 |
|---|---|
| 领域规则 | 约束、不变式、状态转移和异常路径；存在领域事件时验证其语义 |
| 应用用例 | 编排、成功与失败路径；使用事务时验证边界，测试替身用于隔离外部能力 |
| 持久化（使用时） | 按实际数据库、文件或平台存储验证读写、映射、恢复和原子性；真实数据库测试仅用于数据库实现 |
| API/Adapter | 契约、校验、鉴权、错误映射、协议转换和必要的幂等 |
| 架构 | 约定的模块边界、依赖方向和循环依赖；以现有平台约束和本次改动为准 |
| 事件机制（使用时） | 实际采用的投递、重复处理、重试、投影或重放机制 |

采用丰富领域模型时检查贫血模型、上帝 Service、聚合过大、跨聚合对象引用和基础设施泄漏。简单数据对象或平台框架依赖本身不构成阻断问题。覆盖率用于发现遗漏，采用项目已有门禁，不把参考百分比直接变成强制标准。

**产出**：测试报告、架构检查结果、按严重程度排序的问题及修复结果。阻断级问题未解决时，不进入交付。

### Step 9：完成交付和运行保障

根据项目实际交付范围完成：

- CI 中与影响范围匹配的标准构建、测试和适用的架构检查。
- 配置和秘密信息管理；使用数据库且结构变化时提供可重复执行的迁移。
- 按运行环境提供诊断与可观测性；使用可靠消息机制时监控积压、失败和延迟。
- 最简单满足需求的部署方案、回滚方案和运行说明。不要因为使用 DDD 就默认引入 Kubernetes 或微服务。

**产出**：与交付环境匹配的构建部署流程、配置、诊断和回退说明，不套用无关技术栈的部署模板。

### Step 10：同步文档并持续演进

文档贯穿上述步骤，而不是最后补写：

- 业务或上下文变化时更新统一语言、事件时间线和上下文映射。
- 聚合边界或关键规则变化时更新领域模型文档。
- 重要架构取舍发生时记录 ADR。
- 接口变化时更新 API 文档；按需维护 C4 Context/Container 图。
- 交付受阻或业务显著变化时重新评估架构，不追求无意义的最高成熟度等级。

## 存量项目的执行分支

存量改造先建立现状，不直接套目标架构：

1. 检查代码、依赖、数据模型和现有测试，画出当前上下文及依赖关系。
2. 区分代码级问题与架构级问题，优先修复阻断交付的领域泄漏、循环依赖和错误一致性边界。
3. 选择一个低风险但具有代表性的用例做垂直切片迁移，验证新模式后再扩大范围。
4. 使用渐进替换，保留可回退路径和必要的行为回归测试；不进行无验收标准的大爆炸重写。

## 每次迭代的完成定义

按本次任务范围检查以下条件；未使用的能力标注不适用。环境受限时报告已实现和已验证的边界，并列出剩余步骤，不将未运行的验收标记为通过：

- 用户要求的行为通过相应入口验证；需要端到端或设备验收的场景已有实际证据。
- 改动影响范围内的构建、关键规则、异常路径和回归测试通过。
- 模块职责与依赖符合项目约定，没有新增阻断正确性或交付的问题。
- 使用的持久化、接口契约、授权、错误处理及必要的幂等行为已验证；数据库迁移只在使用且变更时要求。
- 使用可靠事件投递时，失败恢复和重复处理已验证；使用事件溯源时，重放与版本兼容已验证。
- 受影响的模型、接口、架构决策和运行文档已同步，不为局部修改强制创建全套文档。
- 无法验证或尚未完成的部分已明确说明，没有以架构设计代替实际交付。
