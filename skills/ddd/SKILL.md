# DDD

用于从业务需求到可运行、可测试、可交付系统的领域驱动设计。处理完整项目时，按下面的开发主流程推进，不能只给架构建议、目录骨架或资料清单。用户只要求某个阶段或单点问题时，直接完成对应工作，不擅自扩展到全项目。

## 执行原则

1. **先业务后技术**：先理解业务行为、规则和边界，再选择框架与架构。
2. **先打通再扩展**：优先完成一个核心用例的端到端垂直切片，再迭代其他用例；不要一次生成所有层的空壳。
3. **架构五选一**：Layered、Onion、Hexagonal、Clean、COLA 是基础架构备选，不叠加使用。CQRS、Event Sourcing、BFF 和微服务按证据引入，不是默认配置。
4. **以真实项目为准**：先检查现有代码、依赖、目录约定、构建和测试命令。参考材料以 Java/Spring Boot 为主，不得无条件照搬。
5. **按需读取资料**：只打开当前步骤需要的参考模块及其具体文件，不批量加载全部参考资料。
6. **完成必须可验证**：用户要求实现时，必须运行项目标准构建和测试，并实际验证核心场景；只生成代码或只通过编译不算完成。

## DDD 项目开发主流程

```text
业务目标与约束
  → 事件风暴与统一语言
  → 限界上下文与上下文映射
  → 聚合和领域模型
  → 基础架构与 CQRS 等级选型
  → 一个核心用例端到端打通
  → 按用例迭代扩展
  → 测试、架构审查与质量门禁
  → 交付、监控、文档和持续演进
```

### Step 1：明确业务目标、范围和约束

先回答以下问题：

- 系统服务哪些角色，最重要的 1～3 个业务场景是什么？
- 哪些业务规则、状态变化和异常分支构成真正的复杂度？
- 项目是新开发还是存量改造？现有痛点和期望收益是什么？
- 技术栈、团队规模、领域专家、交付周期、数据一致性、部署和合规约束是什么？

同时判断 DDD 是否适用。简单 CRUD、短期原型或缺少业务规则时，选择更简单的实现；不要为使用 DDD 而制造复杂度。

**产出**：项目简报，包含目标用户、核心场景、业务约束、技术约束、成功标准、初步核心/支撑/通用子域，以及所有关键假设。

**进入下一步的条件**：核心场景能够用业务语言完整描述，并知道本次迭代不做什么。

### Step 2：用事件风暴梳理业务并建立统一语言

选取核心场景，按时间顺序梳理主流程和异常流程：

1. 用过去式记录领域事件，例如 `OrderPaid`。
2. 为事件补充触发命令、执行角色、业务规则和外部系统。
3. 标记流程转折点、争议点和尚未明确的规则，不用技术方案掩盖业务问题。
4. 汇总业务术语，确保后续模型、接口、代码和文档使用同一语言。

**产出**：

- 事件时间线：`顺序 | 角色 | 命令 | 领域事件 | 业务规则 | 异常/Hot Spot`。
- 统一语言表：`术语 | 业务含义 | 同义词 | 使用边界`。
- 热点清单和需要领域专家确认的问题。

**进入下一步的条件**：每个核心事件都有业务含义和触发来源，异常流程及未决问题已显式记录。

### Step 3：划分限界上下文并设计协作关系

根据业务语言、规则一致性、数据所有权、团队职责和变化频率划分限界上下文，而不是按数据库表或技术层拆分。

为每个上下文明确：

- 业务职责、核心能力和拥有的数据。
- 核心/支撑/通用子域属性。
- 上游与下游依赖，以及同步调用、领域事件、防腐层等协作方式。
- 独立部署、扩缩容和团队自治是否真的有需求。

默认先形成清晰的逻辑模块。只有部署节奏、扩展需求或团队所有权确实不同，才进一步拆成微服务。

**产出**：上下文清单和上下文映射图，能够看出每个上下文的职责、模型所有权及集成关系。

**进入下一步的条件**：同一业务术语在不同上下文中的含义已澄清，数据归属和跨上下文一致性方式明确。

### Step 4：设计聚合和领域模型

优先设计核心上下文。对每个聚合完成以下工作：

1. 区分实体和值对象，选择聚合根。
2. 按业务不变式确定一致性边界，不按照页面或表结构拼聚合。
3. 定义业务行为、状态转移、约束和异常路径。
4. 定义真正有业务意义的领域事件及其触发条件。
5. 定义 Repository 接口；只有跨实体且不属于单个实体的业务规则才放入领域服务。

建议用下表形成可直接编码的模型：

| 上下文 | 聚合/聚合根 | 实体与值对象 | 关键不变式 | 业务行为 | 领域事件 | Repository |
|---|---|---|---|---|---|---|

**进入下一步的条件**：

- 一个事务原则上只修改一个聚合，跨聚合通过 ID 引用。
- 值对象不可变，实体包含业务行为而不是只有 getter/setter。
- 领域模型不依赖 Web、ORM、消息框架等基础设施。
- 应用服务只编排用例，不抢走领域业务规则。

### Step 5：选择基础架构和 CQRS 等级，记录决策

根据已明确的业务和团队约束选择一种基础架构：

- 小团队、DDD 入门或三层渐进改造：优先 Layered。
- 多入口或外部实现替换需求明显：优先 Hexagonal。
- 需要领域居中的同心层与依赖倒置：考虑 Onion。
- 大型系统、UseCase 驱动和严格模块隔离：考虑 Clean。
- Java/Spring Boot 且需要 COLA 规范、扩展点和脚手架：考虑 COLA。

然后确定：

- 各层职责、允许依赖方向、包和模块结构。
- 领域对象、持久化对象、传输对象和视图对象的边界及转换位置。
- 事务、异常、鉴权、事件发布分别由哪一层负责。
- CQRS 等级：默认 L0；读写逻辑分化时用 L1；读写存储需要独立优化时评估 L2；只有审计、重放和时间查询等明确需求才评估 L3 Event Sourcing。

**产出**：架构图、目录与依赖规则、CQRS 决策，以及记录备选方案、理由和影响的 ADR。

**进入下一步的条件**：能解释为什么选择该架构、为什么不选择更复杂方案，并能指出依赖规则如何被自动检查。

### Step 6：端到端实现一个核心用例

选择业务价值高且能代表领域复杂度的一个用例，例如“创建订单”，先打通完整垂直切片。不要先创建所有聚合、所有接口或所有空 Service。

按以下顺序推进：

1. **定义用例契约**：输入、输出、前置条件、成功结果、业务异常和验收场景。
2. **实现领域行为**：聚合、值对象、不变式、状态转移和领域事件，同时编写领域单元测试。
3. **实现应用用例**：编排领域对象和端口，明确事务边界，不写具体 SQL 或 HTTP 逻辑。
4. **实现基础设施**：Repository/Gateway 实现、领域对象与持久化对象转换、数据库迁移和外部客户端。
5. **实现接口适配**：Command/Query DTO、参数校验、认证授权、错误映射；写操作按需设计幂等。
6. **装配并真实运行**：启动应用及依赖，执行真实 API/CLI/消息调用，验证成功路径和关键失败路径。

**产出**：一个可运行的核心用例、必要的数据库迁移、接口契约、分层测试和实际运行结果。

**进入下一步的条件**：核心场景已端到端验证，而不只是类已生成、模块能导入或项目能编译。

### Step 7：按业务用例迭代扩展

重复 Step 6，一次增加一个可验收用例：

- 优先补齐同一核心流程，再扩展其他上下文。
- 新业务规则优先落在领域模型，不堆进 Controller 或上帝 Service。
- 简单查询保持简单；只有读写模型确实分化时才升级 CQRS。
- 跨聚合或跨服务事件需要可靠投递时，采用 Outbox、消费者幂等、重试和死信等机制。
- 业务理解变化时，先修正统一语言和模型，再调整代码，不让代码与业务术语分叉。

每个迭代都保持可构建、可测试、可部署，避免长时间停留在半成品架构改造中。

### Step 8：执行测试、代码审查和架构质量门禁

| 范围 | 必须验证的内容 |
|---|---|
| 领域层 | 值对象约束、聚合不变式、状态转移、异常路径和领域事件；不依赖框架 |
| 应用层 | 用例编排、事务边界、成功与失败路径；外部端口使用测试替身 |
| Repository | 使用真实数据库验证聚合读写、映射、约束和事务行为 |
| API/Adapter | 契约、校验、鉴权、错误映射、协议转换和必要的幂等 |
| 架构 | 依赖方向、领域纯净度、循环依赖和禁止跨层调用 |
| 事件机制 | 使用时验证 Outbox、重复投递、重试、投影或事件重放 |

同步检查贫血模型、上帝 Service、聚合过大、跨聚合对象引用、基础设施泄漏和 DTO/领域对象混用。覆盖率用于发现遗漏，不代替关键业务路径验证。

**产出**：测试报告、架构检查结果、按严重程度排序的问题及修复结果。阻断级问题未解决时，不进入交付。

### Step 9：完成交付和运行保障

根据项目实际交付范围完成：

- CI 中的标准构建、测试和架构检查。
- 可重复执行的数据库迁移、外部化配置和秘密信息管理。
- 日志、指标、链路追踪和健康检查；使用事件时监控 Outbox 堆积、消费失败和延迟。
- 最简单满足需求的部署方案、回滚方案和运行说明。不要因为使用 DDD 就默认引入 Kubernetes 或微服务。

**产出**：可重复的构建部署流程、运行配置、监控告警和回滚说明。

### Step 10：同步文档并持续演进

文档贯穿上述步骤，而不是最后补写：

- 业务或上下文变化时更新统一语言、事件时间线和上下文映射。
- 聚合边界或关键规则变化时更新领域模型文档。
- 重要架构取舍发生时记录 ADR。
- 接口变化时更新 API 文档；按需维护 C4 Context/Container 图。
- 交付受阻或业务显著变化时重新评估架构，不追求无意义的最高成熟度等级。

## 存量项目的执行分支

存量改造先建立现状，不直接套目标架构：

1. 检查代码、依赖、数据模型和现有测试，画出当前上下文及依赖关系。
2. 区分代码级问题与架构级问题，优先修复阻断交付的领域泄漏、循环依赖和错误一致性边界。
3. 选择一个低风险但具有代表性的用例做垂直切片迁移，验证新模式后再扩大范围。
4. 使用渐进替换，保留可回退路径和必要的行为回归测试；不进行无验收标准的大爆炸重写。

## 每次迭代的完成定义

只有同时满足以下条件，才能把当前用例报告为完成：

- 用户要求的业务场景已通过真实调用端到端验证。
- 关键不变式、异常路径和回归测试通过，项目标准构建与测试命令通过。
- 领域、应用、接口和基础设施职责清晰，没有新增阻断级架构违规。
- 数据库迁移、接口契约、鉴权、错误处理和必要的幂等行为已验证。
- 使用事件时，可靠投递和重复消费场景已处理。
- 相关模型、API、ADR 和运行文档已同步。
- 无法验证或尚未完成的部分已明确说明，没有以架构设计代替实际交付。
